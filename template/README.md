# A new connector

A connector is a small folder: `src/definition.ts`, which exports `connector()`, what the connector is and what one run reads from its vendor, and `src/main.ts`, which starts it, beside the type it writes and any helpers its vendor needs. The kit, `@withmarfa/connector`, does the rest:

- registers the connector on every start;
- refuses a key whose permissions, type, connection and extension maps, profile fields, source claims or enforcement overrides reach beyond the connector's own types and connections, as [The key](#the-key) lists;
- reads the connector's settings from Marfa at the start of every run, typed by kind, and keeps every secret out of the log;
- checks the types and connection types the installed plugin holds against its build, registers none, and writes without an optional field or table the installed type lacks, saying so until the plugin is updated;
- compares what the run found with the rows already written, and writes only what changed;
- heartbeats, keeps the connector's state, and reports each run;
- takes the webhooks a vendor posts, where the connector reads them.

## The job

A connector does four things, and the kit carries all but the vendor's side of each:

1. **Registers.** On every start the kit registers the connector with the instance, reads the key back and refuses one that is wrong, then checks each type and connection type the connector declares against the instance's, which installing the connector's plugin registered; the kit registers none. The connector declares its `name`, `source`, `sourceName`, optionally `sourceMark`, `types` and `settings`; its connector host mints the key ([The key](#the-key)).
2. **Reads.** `run` reads the vendor, and hands what it found to `upsert` and what the vendor deleted to `archive`. The kit writes only what changed. A scheduled run reads the vendor whole.
3. **Delivers.** A connector that also carries changes made in Marfa back to its vendor declares `link_field` on its type and an `onChange` ([Carrying changes back](#carrying-changes-back)). A vendor that cannot take a change says so by throwing `Unreachable`, `Refused` or `Declined`, and the run goes on.
4. **Reports.** The kit reports each run to the instance as succeeded or failed, with a summary. A problem that lasts but lets the run go on is `log.condition`. An error thrown from `run`, such as a vendor refusing the token, fails the run, and the process exits with code 1 under `--once` ([Exit codes](#exit-codes)).

## Start one

1. Copy the template's files without its build output and installed packages, and set `name` in the copy's `package.json` to `<name>`:

   ```bash
   mkdir connectors/<name>
   cp -R template/connector/package.json template/connector/tsconfig.json template/connector/src template/connector/test template/connector/plugin connectors/<name>/
   ```

   A plain `cp -R` also copies a built `dist/` and `node_modules/`, and a stale file left in `dist/` survives the next build. The folder sits at a connector's depth, so its paths hold once copied.

2. Add `{ "path": "connectors/<name>" }` to the references in the root `tsconfig.json`. Until it is there, the tree test fails `pnpm test`, since the build would skip the connector.
3. Replace `src/example.item.json` with the type the connector writes, and in `src/definition.ts` name the connector and the plugin it is published as (`title`, an Iconify `mark` and `maker`), its source, the source's name and mark, and its `types`, each a kind with a `name`, a `direction` (`in`, `out` or `both`) and a type with the `fields` the vendor holds, declare the `settings` it reads, and write `run`. A connector may write up to ten types, such as issues, comments and files, each with its own fields, read-only fields and link. The example's type names no `parent`: it stands alone, with every field its own. Where the vendor's rows read as a core type, such as a task or a bookmark, the type file names that core type as its `parent`, as `connectors/todoist/src/todoist.task.json` does with `core.task`, and adds only the vendor's own fields; `run` then writes the core type's fields under the core type's names. Each setting has a `name` in lowercase snake case, a `label`, a `kind` (`text`, `number`, `boolean` or `choice`), and where they apply `secret` (text only, never with a `default`), `default`, `required` and `choices`; the owner sets each in Marfa, and the kit reads them from there. Keep the definition in `src/definition.ts` and export it as `connector()`. Read no `process.env` there: a definition that changes with a setting takes `connector(settings)`, `main.ts` hands `connector` itself to `main`, which builds it again from the settings Marfa holds at the start of every run, and the definition exports `widest`, the settings that give it its widest shape, since the key a host mints for the plugin writes only the types of its kinds. Write the guidance for each type, at most 1,000 characters, in `plugin/types/<id>.md`, as the example does. After `pnpm build`, run `pnpm connectors:generate` to write the rest of `plugin/`: `plugin.json`, a type file for each kind and an edge type file for each connection type Marfa does not ship. `pnpm connectors:check` fails when any is out of date or a type has no guidance.
   A field a type names as its `body_field` holds Markdown. A connector whose vendor sends HTML for one converts it first with `htmlToMarkdown` from `@withmarfa/connector/markdown`: text without HTML passes through unchanged, and it throws `NotConvertible` for markup past the kit's limits on length, elements or nesting, which the connector handles by leaving the field out. A connector whose vendor takes HTML back converts a body with `markdownToHtml`, which throws the same error, with a `reason` of `length`, `depth` or `complexity`, for Markdown past 100,000 characters, nested deeper than it reads or costly to convert; the connector refuses that write.
   A connector whose vendor names a picture by a web address fetches it with `fetchPicture` from `@withmarfa/connector/pictures`, which returns the picture's `bytes` and `mime_type` for a `FileSource` to upload, or `{ ok: false, reason }`, which for `bad_status` also carries the answer's `status`, so that a 404 can be told from a 429 or a 503. It makes one `GET` over `https`, with a fixed `User-Agent` and no credentials, cookies or referrer, and follows at most four redirects. It refuses an address that is, or resolves to, this machine or a private network, at the first request and at every redirect, unless the connector passes the host in `privateHosts` (`privateHostSet` from `@withmarfa/connector/network` reads a setting's value into that set). It stops at 25 MiB, by the length the server declares and by the bytes it sends, and after 30 seconds. It decides the type from the first bytes, never from the server's header: PNG, JPEG, GIF, WebP, AVIF and HEIC are pictures, and SVG never is. It reads the size from those bytes, and refuses a picture one pixel wide or high, a picture that claims more than 100 million pixels, and the counting pixels of known trackers. The reason is one of `invalid_address`, `not_https`, `private_address`, `tracker`, `too_many_redirects`, `bad_status`, `too_large`, `timed_out`, `fetch_failed`, `not_a_picture`, `svg`, `one_pixel` and `too_large_dimensions`; a connector keeps the code, not the words. The function throws only when the `signal` it is given aborts.
4. `test/connector.test.ts` runs the example as a process against a scripted server and a stub vendor. Rewrite it for yours. It imports the scripted server from `kit/test/scripted-server.js` by a relative path, as every connector's test does. That is an exception to the rule that only the kit's package is imported: it is a test helper, and nothing built into the connector reaches it. `test/quiet-run.test.ts` runs the kit's shared quiet-run test: a run that finds nothing new at the vendor may send Marfa at most one more request for each 200 rows Marfa holds. Keep it, with `hold` starting your vendor's stub holding the given number of items; the tree test fails `pnpm test` for a connector without it.
5. `pnpm install && pnpm build && pnpm test`. The install adds the connector to `pnpm-lock.yaml`, which CI installs frozen, so commit the lockfile with the connector.

### What the example does

The example vendor lists every item on `GET items` as `{ account, items }`, answers one on `GET items/<id>`, and takes `POST items`, `PUT items/<id>` and `DELETE items/<id>`. Replace those calls with the vendor's; keep the behavior:

- **The source has a name and, where Marfa's icon sets have one, a mark.** `sourceName: "Example"` is what an app shows for the source instead of its code, and `sourceMark` is an icon ID from the `simple-icons` or `lucide` set Marfa accepts, such as `simple-icons:github`; the example declares no mark, since neither set has one for it. On every start the kit reads the source (`GET /sources/{source}`) and sets with `PATCH /sources/{source}` only what the owner has not set, so a name or mark chosen in an app outlasts a restart. If Marfa refuses the call, for example a mark outside its sets, the kit logs a warning, the connector still starts and syncs, and the next start tries again; an answer that does not come ends the attempt like any other call of the start. The name is the system, not the route the data came by and not an account.
- **Every vendor call has a time limit.** `example_timeout_ms`, 30000 milliseconds unless it is set, covers the answer and its body, beside the kit's `signal`. A vendor that does not answer in time is treated as one that did not answer at all: from `onChange` or `remake` that is `Unreachable`, so the change is sent again next run, and from `run` it fails the run, which the next scheduled run tries again. Without a limit, a vendor that never answers stalls the run, and nothing in the kit but a stop ends the call.
- **The settings are checked before each run.** `checkEnv` refuses an `example_url` that is not an http or https address and an `example_timeout_ms` that is not a whole number of milliseconds from 1 to 2147483647, naming the setting and never its value. The run stops having written nothing, and the process exits with code 4.
- **A base address with or without a trailing slash reaches the same place.** `new URL(path, base)` drops the base's last segment when the base lacks the slash, so the example adds one: `https://vendor.example.com/api` and `https://vendor.example.com/api/` both reach `/api/items`.
- **A row the vendor stops listing is asked about.** An item marked `deleted` is archived. An item left out of the listing is read back from the instance with `held`, and the vendor is asked for it: if it answers 404, or answers that the item is deleted, the row is archived; if it still has it, the row is left as it is, since a listing that leaves something out is not the vendor deleting it. A row archived this way comes back when the vendor lists it again. Any other answer, a rate limit or a server error included, stops the asking and fails the run once the listing's rows are written and what is certain is archived, and the next scheduled run asks again.

What a run has to hand:

- **`upsert(type, entries)`**: each entry is a `source_id`, its properties and its `occurred_at`. Put the vendor account inside the `source_id`, as `<account>:<id>`, only for what that account owns, such as a calendar or a mailbox, so two accounts under one source never share a row; an id the vendor makes unique across accounts, such as a global node ID, needs no account. A property that is absent or `null` is cleared from the row. Every property an entry carries is among its type's `fields`, the properties the vendor holds; an entry carrying another is refused with a condition. A row's other properties are Marfa's own and never touched. A row the instance refuses is held with a condition naming it and the instance's reason, and the run goes on; the next run that reads it writes it again. A row a person retyped, to a type the key may not write or to another of the connector's types, cannot be mended by writing it again, so its condition stands for as long as the vendor names the row, and it holds back nothing else. A refusal every write would meet fails the run instead: an instance that does not answer, a key it refuses or one narrowed so it no longer writes the connector's types, the connector's own source refused a create of its type, or every row one call wrote refused alike.
- **What the vendor changed, field by field.** For each row the kit keeps, on the instance, what each side last held, field by field. An entry is written only where the vendor changed something since, and only the fields it changed: an edit made in Marfa to another field stays. A field both sides changed goes to the later change, by the entry's `changed_at` and when the edit was first seen in Marfa, and a tie to Marfa; the run names the row and the field that lost. An entry older than what the two sides last agreed on is left unwritten. A row that nothing was agreed for, as after the connector's state was cleared, takes the vendor's value wherever the two differ, and the run says how many.
- **`archive(type, keys)`**: for what the vendor deleted, by natural key, or by the vendor's id where the type names a link. A row is archived, never trashed, and a row a person trashed is never touched. A row archived this way comes back when the vendor sends it again; one a person archived stays archived.
- **What a run reads.** Only the rows its entries, the log and the changes waiting name, looked up by link, natural key or id in every state; the type is listed whole only when the log no longer holds the cursor.
- **`connections`**, on the connector, with `connections` on an entry: kinds of connection between the connector's own rows, such as an issue's sub-issues, each an edge type as the plugin's `edge-types/` folder installs it, both ends constrained to the connector's types, orphaning on delete, and requiring no property, since the kit writes none. Installing the plugin registers the custom connection types, and the kit only checks them: one that is missing, or that differs beyond endpoint lists the installed type takes wider, stops startup. The built-in `attached-to`, `in-collection`, `in-thread`, `references`, `excerpt-of`, `about`, `comments-on`, and `parent-of` types are checked, never changed, and a declaration repeats the instance's own `cascade_on_delete`; declare both ends as the connector's own types and grant only the corresponding edge permissions. `parent-of` cascades on delete, and a row attached through `attached-to`, or a comment on a host through `comments-on`, goes into the bin with its hosts (`cascade_on_delete: "with-hosts"`); a custom connection type must orphan, and the kit refuses one that does not. A recurring event's changed occurrence joins its series through it, as the next item describes. An entry's `connections` names, for each connection type, every row its row points at, by type and by link, or natural key where the type names no link, and an empty list where there is none; a type left out is left as it is, and one never named has nothing agreed, so a change made to it in Marfa is not carried. They are written once the run's rows are, so a target made in the same run is found, and one Marfa does not hold yet is connected when it arrives, whether or not the vendor names it again. A connection made or removed in Marfa is carried to `onChange` as `change.connections`, the rows at the other end, or put back where the row's type is read only; one a purge took is never carried, and one from the connector's row to a row outside the declared ends, such as a person attaching a file to their own note, is theirs and left alone. A connection a person moves to another row, which Marfa keeps as the same edge, is carried, or put back, as a removal and an addition. Where the connector's row is the end that stays, that is one change for that row: the row the connection left among `removed` and the row it reached among `added`. Where the connector's row is the end that moved, which only a `one-to-one` or `one-to-many` connection allows, it is a change for each of the two rows, the row it left and the row it reached, in no set order. Where the kind only reads, the kit puts back every connection a run found changed in one pass, removing every connection it removes before it draws any, so a target that holds only one connection is free when the row it left draws it again. Marfa names only the row it reached, so the kit finds the row it left by reading every agreement the connector keeps, 200 to a request, once in the run; it skips the read when the row the connection reached already agrees with it. A change to a connection's properties alone carries nothing. Where nothing is agreed for a custom connection type, as after the connector's state was cleared, the vendor's set is taken and nothing carried. For `references`, `excerpt-of` and `about`, only previously agreed or currently requested targets are reconciled; other references are left alone, including references to another item of the connector's own type.
- **`retired`**, on the connector: `{ type, connection }` pairs for a connection a row of that type once wrote and no longer does. Keep the connection among `connections` and name it with an empty list on each entry of the type. The kit then removes only the edges it had agreed with that row, in every mode including read only, so a link a person drew is never removed, and never mirrors or puts back a change to it. Without it, a connection an entry stops naming stays on rows written before, because a write replaces only the edge types it names. The key keeps write on the retired edge type.
- **A series and its exceptions**, through the instance's `parent-of`, which Marfa itself uses to join a changed occurrence of a recurring event to its series, from the series to the exception. Declare it among `connections` with both ends the connector's own types, in the direction the vendor names it. A vendor whose exception names its series declares the reverse name `child-of`, read from the exception's side as every declaration is: `many-to-one`, `cascade_on_delete: "cascade"`, the exception's types as `from_type_constraints` and the series' as `to_type_constraints`, and the exception's entry names the series in `connections: { "child-of": [{ type, id }] }`. A vendor whose series names its exceptions declares `parent-of` (`one-to-many`, also cascading) and the series' entry names them. Declare only one of the two, since they are one edge type, and the key holds `--edge-permission parent-of=write` for either. The kit writes `parent-of` from the series to the exception in both cases, after checking that the declaration matches the instance's own, which it never registers or changes; for `child-of` the check turns the instance's cardinality about, since it is read from the other end. An exception has one series, so naming another moves it, the old connection removed first. A series that has not arrived yet is connected when it does, and the other rules of `connections` hold. One limit applies to `child-of`: no type among its ends may have a `policy`, since the instance can condition an edge's write only on the version of its source, which is the series. A lookup carries only the edges that start at a row, so the kit reads a series from the other end. For eight rows or more of the `child-of` source types, it lists the instance's `parent-of` edges, 500 to a page, and keeps those that point at the rows it is reading, so the cost is one request for every 500 `parent-of` edges in the instance and not one for each row, series and plain events included where they share the exception's type. The pages count every `parent-of` edge, including those of other connectors and of a person's own hierarchy that the key may not read. It gives the listing up for one request for each row when the listing would take more pages than there are rows, so a small run in an instance with many `parent-of` edges costs at most twice its rows. A rate limit or other failure of these reads fails the run, as any other read of Marfa does, and the next run reads again.
- **`file`**, on an entry of a file type: a type whose `parent` is `core.file` or one beneath it, whose `fields` list `blob_ref` and `mime_type`. It gives the vendor's own key for the bytes, such as an etag or asset id, and `load`, which fetches them, whole or as a stream such as the vendor's response body; a stream is uploaded as it is read, never held whole, and the upload is cut off only when it goes quiet for the request time limit, never for its length. The kit loads and uploads the bytes only when that key differs from the one it last uploaded, in the run that writes the row, and writes the answer as `blob_ref` and `mime_type`; the instance then reads text and image dimensions from them. Bytes the vendor would not give, or a stream of them that breaks or goes quiet, are a condition, and the row waits; an upload the instance refuses, such as a file of no bytes, holds the row as any refusal of it does. A file attaches to its item through the instance's own `attached-to`, declared among `connections` with `cascade_on_delete: "with-hosts"` and both ends narrowed to the connector's types, so trashing the item puts its files in the bin and restoring it brings them back; the kit never registers it, and the key holds `--edge-permission attached-to=write`. A message joins its thread the same way, through the instance's own `in-thread`, such as a comment on its issue. The kit writes no `position` on it, so the thread's order is the messages' own time, and since a message is in one thread, one a person put in a thread of their own is left there and the vendor's thread refused, with a condition. A row joins a collection through the instance's own `in-collection`, whose target types must have the `container` role, as a type extending `core.collection` does; the kit writes no `position` on it either, and a collection cannot itself be a member, so collections nest through `parent-of`.
- **A purge is remembered by the instance.** An entry naming a row a person purged is not written back, however long after and whatever the connector's state, until the vendor changes it after the purge; it then comes back as a new row. The run says how many entries it held back.
- **`linked(type, connection, target, options)`**: the active rows of a type holding a connection of that kind to a row the target names, such as a repository's issues, read from the instance: what Marfa holds under something, so a connector can find what its vendor no longer lists and ask the vendor about each. Only rows of the type itself that the vendor has been told about are answered, unless `options.rows` is `"all"`, which answers every active row connected to the target, whoever wrote it and whether or not this process holds an agreement for it, to see what else is held under it. Connections the run's own entries name are written once it ends, so a row they connect shows from the next run, and one they move elsewhere, such as an issue moved to another repository, is left out at once.
- **`linkedEach(type, connection, targets, options)`**: `linked` for many targets of one type at once, `targets` naming the type and the ids, answered as a map from each id to its rows, with no rows for a target Marfa does not hold. It asks Marfa about every target in a few requests, so use it, not `linked` in a loop, whenever a run asks about more than one target. Likewise, ask `held` once per type in a run: it reads every row of the type, 500 to a request.
- **`derive(type, keys, values)`**: sets a type's `derived` fields on the rows held under these keys, by natural key or the vendor's id as `archive` takes them, where the vendor's answer is not to hand, such as for a container no longer readable. It writes only what differs, never to a row in the bin, and agrees the value so it is no change on the next read.
- **`tables.put`, `tables.patch`, `tables.remove`, `tables.replace` and `tables.read`**: the rows of the tables a type declares under `tables`, on the connector's own items, named by the item's link, or by its `source_id` where the type names none. A table suits many small records that belong to one item and are read with it, such as the checks on a pull request, where a separate item for each would be noise. A type's tables are installed with the plugin, and the kit registers and replaces none. A stored type that lacks a table, an optional column, or a first `order` is written around, with no rows written to that table, and the run names `marfa plugins install <name>`; any other table change stops the start and names the differences. A row is `{ key, values }`, and its id in Marfa is made from the key, the item and the table, so a run sent again writes the same rows and never a second. `put` creates or replaces rows, `patch` sets the columns named, `remove` deletes rows by key, and `replace` makes the table hold exactly the rows given, writing only those that differ and deleting the rest, so a row the vendor removed is removed. A table on a connector's type belongs to the connector: `replace` deletes every row the vendor did not list, including one a person added in Marfa. A changed `label` or `description` on a table or column is no difference, and the kit does not replace the type. Upsert the item first: a call writes nothing for an item Marfa does not hold, or one in the bin, and says so in its report's `skipped`. Pages stay within the server's limits. Each call makes one random value, and a page's idempotency key comes from that value, the item, the table and the page's operations, so a retry within the call reuses the key and a later call or run gets a new one: a value that returns to an earlier state is written again, never replayed from the server's 30-day memory of a key. The server writes a page whole or not at all, so a row it refuses, such as a value over a column's `max_length`, is left out and named in the report's `refused` and in a `table-rows:<type>:<table>` condition, and the rest of the page is written. Any other failure throws.
- **`known(type, keys)`**: returns a detached set of the requested natural keys, or vendor IDs for a linked type, whose rows have an agreement under that identity. Active, archived, and trashed rows are included; missing or purged rows and manually assigned identities without an agreement are excluded. The lookup does not restore or update rows and does not establish whether the vendor still has the item. Available on root and scoped run contexts.
- **`held(type)`**: the active rows of a type that carry a value for its link, or, for a type without one, that it wrote under its own source, read from the instance, whatever their connections and whether or not the vendor was told of them, so a row a person made by hand with a link value of their own is among them, and asking the vendor about it, as the example does, finds it has no such item: what Marfa holds of the type, for a vendor whose listing leaves out what it deleted, such as one that lists only open items after it lost its place, so the connector can ask the vendor about each row its listing left out. With `{ state: "any", edges: true }` each row also carries `edges`, its outbound connections as `Item.edges` has them (the first page of each connection type), read in the same pages of up to 500 rows, so what the rows are connected to is known without a request for each. Connections a run names are written when it ends, so they show from the next run.
- **`written(type)`**: the fields of the type the kit writes now, which are the `fields` the connector declares for it, less any the installed type lacks (see below), so it changes when that narrowing begins or lifts. A connector that reads by delta, such as with a sync token, brings a field onto a row it already holds only when the vendor changes the row, so it should include these fields in whatever marker makes it read in full.
- **`state.get` and `state.set`**: a small value kept between runs, such as a sync token. It is kept on the instance, under the key's own source, and only when every write in the run landed, so a connector needs no disk of its own and can start anywhere, empty.
- **`forScope(name)`**: bind row calls to one read scope without adding stored scope fields. Await each scoped operation serially. Two unfinished scopes touching the same item cannot checkpoint; finish one before the other changes that item. Root calls may run concurrently and their shared operations are queued. Mixing root calls with an active scoped operation is refused. An operation or checkpoint left in flight when `run` returns fails the run.
- **`forScope(name).state.get(key)`**: a detached value from the last acknowledged vendor state, including checkpoints completed earlier this run. It does not read the mutable root draft.
- **`forScope(name).state.checkpoint(key, value)`**: explicitly await a JSON-compatible candidate after completing that scope's read. The kit clones it, drains that scope's connections, acknowledges its prerequisite agreements, then replaces the existing full state envelope through the same fenced door used at the end of a run. Applicable edges must land first; absent targets must be durably named in the existing pending connection agreement. A completed checkpoint survives a later failed scope or process restart. The API replaces the explicit JSON value; it does not merge vendor fields. When scopes share a map key, build each candidate from that scope's latest acknowledged `get(key)` plus only its completed entry. Reusing a run-wide speculative map could wrongly save an earlier blocked scope's validator. It keeps the last acknowledged log cursor and standing conditions; it neither clears conditions nor rotates a report mid-run. Ordinary row and edge writes are not a transaction and may already have landed when a checkpoint fails, so replay remains necessary.

  The awaited result is `{ committed: true }` or `{ committed: false, reason }`. Blocking reasons are `row-refused`, `agreement-skipped`, `agreement-oversized`, `connection-unresolved`, `scope-overlap`, and `state-oversized`. A nonterminal row refusal blocks even if its usual final-only handling counts no held row. Skipped agreements block conservatively without querying whether the item was hidden or purged; oversized agreement intentions remain pending rather than being cleared. An unrelated scope can still checkpoint. No refusal journal or automatic cursor is created. Non-JSON input, transport failures, malformed acknowledgments, lost holds and concurrent scoped use throw. Checkpoints require a successfully loaded state and an active full vendor read; a hinted read cannot advance whole-source progress.

  The private state envelope and the explicit problem snapshot must each fit 512 KiB, independently, and each required agreement must fit 16 KiB. A clear acknowledgment counts agreements actually deleted, so an accepted clear of a readable item without an agreement correctly returns zero. If either member of a state acknowledgment is lost, different, or ambiguous, every later mutation and final save stops: the server may have committed it, and sending an older envelope would roll progress back. The next process reloads authoritative state. The existing root `state.get/set` API still saves its draft only when the whole run's writes land; a later failure falls back to the latest acknowledged checkpoint.

A scope may opt into bounded inbound upsert retries with `forScope(name, { retry: { mode: "refetch" | "replay", context } })`, where `context` is a full SHA-256 of the caller's relevant nonsecret retry configuration. `scope.refusals.pending()` returns detached, acknowledged records with a derived `due` flag. Refetch mode requires the caller to retrieve each saved exact identity and reconstruct its complete current upsert. Replay mode stores a lossless JSON upsert intent; the caller dispatches due saved operations through ordinary scoped `upsert`. Prefer current complete input over an older replay for the same identity. Missing input, a conditional response, or inaccessible input preserves the record. The kit does not fetch or replay for the caller.

Only complete `invalid_properties` upserts and singleton `request_too_large` refusals after batch splitting qualify. Bounds are mode-specific: refetch stores the complete exact identity, fingerprint, context, refusal and due record; replay must also store the complete round-trip payload. A complete large singleton size refusal may qualify through a genuine point-refetch route even when its replay payload would not fit. File loaders and streams cannot be replayed. Unknown refusals, races, incomplete input, skipped bulk results, and undeclared or missing identities block scoped progress. Callers without a capability, and existing unscoped callers, gain no automatic advancement. A refusal the journal takes does not count toward the systemic-refusal check, even when every row in its batch is refused, so a scope whose new rows the instance refuses for their own content still checkpoints. After excluding those refusals, a batch with at least two remaining attempts fails if every attempt is refused with the same code, such as a code the journal does not take or a refusal the full journal has no room for.

A qualifying refusal and the position commit together in the existing state envelope. Records retain exact identity, intent fingerprint, effective context, and due time. Changed intent or context retries immediately; unchanged intent waits 24 hours after an acknowledged actual attempt. A retry refused again is journaled again, so it stays contained even when every row in its batch is refused. Authority, transport, and journal-capacity failures still block progress. A successful upsert clears a record only after its row, connections, agreement, and state acknowledgment. If the vendor explicitly reports deletion, call `scope.archive(type, keys)` in the same opted-in scope and retry mode, then checkpoint. For linked types, pass the link value as usual. The retry clears with that checkpoint only after an acknowledged archive, an already archived row, or a fresh empty lookup paired with stored evidence that an individual `invalid_properties` insert resolved no existing item when it was refused. An empty lookup alone cannot distinguish absence from a row moved to a type the connector cannot read; rejected updates, size refusals, and records without this evidence remain pending on an empty lookup. Failed or uncertain operations, omitted or unhinted identities, and skipped trashed or manually restored rows retain the retry. An absent Marfa row does not establish vendor deletion; that decision belongs to the connector. Journal limits are 128 records and 64 KiB of serialized UTF-8 JSON across all scopes, independently of the complete 512 KiB state envelope. Capacity blocks without eviction or identity truncation: the checkpoint returns `state-oversized`, and the run raises the condition `retry-journal-full:<scope>`. The condition stands until that scope commits a checkpoint, which proves the journal had room, so a run that skips the scope or commits only other scopes does not clear it. Durable refusals remain visible in the complete run log beyond the generic condition-storage cap. Each checkpoint candidate must start from the latest acknowledged vendor state; the API replaces an explicit JSON value and does not merge speculative maps for the caller.

An unresolved record also prevents switching its scope to a different retry mode or removing its capability. Root state setters remain conservative while a journal is unresolved; independent explicitly capable scopes can still checkpoint from the latest acknowledged map.

- **`log.condition(key, message)`**: something that lasts across runs but lets the run go on, such as a feed that stopped answering among several. Raise it on every run it holds: the kit warns it in the log and carries it in each run's report while it stands, and logs it as cleared once a successful scheduled run reaches its check without raising it. A run that failed, or that deliveries started, clears none, and its report carries what stood before beside what it raised. A report has room for about two thousand characters: the conditions that do not fit are counted in it, named in the log, and carried first in the next report. A run in which the connector read nothing, because every source it reads failed, is thrown as a failure rather than left to succeed with conditions. What stops the run, such as a vendor refusing the token, is thrown instead, and fails the run.
- **`log.unreached({ keys?, prefixes?, exceptKeys? })`**: mark the exact checks skipped this run, using exact condition keys or literal key prefixes. Existing matching conditions stand through a successful scheduled run; a reached check that finds the problem gone can clear it on a later run. Calls accumulate for this run alone. `exceptKeys` excludes exact keys from that call's prefix matches, so a connector can preserve a family with unknown identities while naming the checks it actually reached. Exceptions do not cancel exact `keys` or another call's selectors. Keep unknown identities conservatively when saved progress cannot enumerate every standing condition. Selectors do not raise a condition, create stored state, or override a newly raised message. For example, skipping a feed's access check calls `log.unreached({ keys: ["feed-gone:" + feedId] })`; still raise lasting problems with `log.condition` whenever their checks find them.
- **`signal`**: hand it to `fetch`, so a stop is prompt, and combine it with a time limit of the vendor's own, `AbortSignal.any([signal, AbortSignal.timeout(ms)])`: the kit puts no limit on a run, so a call that never ends stalls it. A call that ran out of time is a failure to answer, as the example treats it.
- **`env`**: the values of the settings the connector declared, each under the setting's name, as Marfa holds them for the connector: the kit reads them at the start of every run, so a value the owner changes between runs is the next run's. Each comes typed by its `kind`: a `boolean` as `true` or `false`, a `number` as a number, a `choice` or `text` as a string, and one not set as its `default`, or `undefined` where it has none. A `required` setting with no value, a secret Marfa cannot open, or a value not of its kind stops the run with one condition naming each setting by label and name, never its value, and the process exits with code 4. A `secret` setting is kept out of log lines, conditions, reports, errors and telemetry from the moment the kit reads it, including during setup, and a secret shorter than eight characters stops the run. The owner sets them with `marfa plugins settings <plugin> --set <name>=<value>`, and a secret with `marfa plugins secret <plugin> <name>`, which reads it from standard input. A secret that holds a list, such as several addresses, is also kept out part by part, where each part is set apart by whitespace or commas and is at least eight characters long. A value the connector can tell is wrong on sight, such as a malformed address, is refused by throwing from `checkEnv`, which stops the start the same way.
- **`secret(value)`**, in `run`, `onChange`, `remake` and `setup`: keeps a value made at run time, such as an installation token, out of every log line, condition and report from then on. A value under eight characters is refused, since it could not be found without redacting ordinary words.

A connector writes its own type, and by default at the feed tier. It may name the library tier only for a row that belongs to something already in the library, such as the picture files of an entry the owner has kept; it never puts what it reads from a vendor into the library on its own. Moving a vendor's row to the library is a person's or an app's act. A connector reads from its vendor; one that is asked to also carries changes made in Marfa back to it, as the next section describes, and never anything else.

## Carrying changes back

Before entering a vendor read, the kit acknowledges pending agreements from its watch observations and completed early carries. An acknowledgment removes ownership only for the exact intent the server accepted. Ordinary outbound field edits still run after the vendor read so they can reconcile with its values. Durable waiting and refusal intent remains in the agreement; acknowledging it does not mean the vendor accepted the change. An unusable prerequisite acknowledgment, including a skipped or oversized intent, a malformed answer, a refusal or a lost response, stops the reader and prevents later agreement retries or state/cursor saves in that process. A new process reloads what the server actually kept.

A two-way connector declares two more things, and the kit's watch phase does the rest:

- **`link_field`**, in each type's definition: the property that holds the vendor's own id for a row. The instance keeps it unique within the type, in every state, and refuses a second row holding the same value with `link_taken`. With a link, every row of the type is the connector's to read and write, whoever created it and under whatever source: an entry finds its row by the link first and by its natural key second, `archive` takes the vendor's ids, and a row carrying no value is one the vendor has not been told about. A row counts as told only once the connector and the vendor agreed on it under the value it carries, so a row made by hand with a value of its own is never taken for one the vendor has: a connection to it waits, and `linked` leaves it out. Every entry `run` hands over carries the link; one without it is refused with a condition. The link is the connector's: a person's change to it is put back, with a condition, before anything is carried by it. A row in the bin cannot have it put back, so its change is carried by the link agreed with the vendor. A purge drops what was agreed, so the kit carries one only by a link it can vouch for: the agreed one, which it keeps from the moment a run reads a link other than it until the agreed one is written back, for up to a thousand rows, or the row's own where every change the run read for the row since then moved it between states, or was the connector's own create, and showed the same link. Any other purge is not carried, and the run names the row; past the thousand, no purge goes by the row's own link until a whole read of the log keeps every such link again. A row whose create was sent and got no link back has no agreed link, so a link it holds since may be a person's: a trash of the row before any later change of it is carried goes with `change.attempted` and no link, and the kit keeps, among those thousand, that no link was agreed, so its purge is not carried by that link either. A change carried while the row is active goes by the link it holds, and so do its trash and purge after that. The example names `example_id`. A type registered before it named its link fails the start until it is replaced with one that does. Say so in the connector's own README: a row of the type made by hand is carried to the vendor, and something meant to stay in Marfa is a row of the core type instead.
- **`onChange(change, context)`**: called once per row with something in Marfa the vendor has not had, with `change.kind` one of `created`, `updated`, `restored`, `archived`, `trashed` or `purged` (a restore's `change.was` saying whether from the bin or from archive), `change.item` the row as it stands, and `change.changed` the fields changed in Marfa and not yet carried, the read-only ones and the link left out. A transition carries the fields changed beside it; a trash and a purge carry none. What of a row travels is the connector's choice; the example sends the title, url and note. It may answer the vendor's entry as its write left it, which the kit takes as what the vendor now holds, so a value the vendor normalizes, or its own close echoed back, is no change; without an answer the carried values are taken as the vendor's. An answer is written onto the row for each field it states, a null as a clear, that the change did not carry and Marfa has not changed since, or that is read-only, such as the number a vendor gave a row it just made, or its reopening on a restore; a field the change carried keeps the person's value. An answer's `connections` are what the vendor holds for each type it names, so a connection the vendor would not take, such as one past its limit, is taken back in Marfa once the run's carries are done; the connector says why with a condition. For a purge, the answer's `changed_at` keeps the purge remembered past the vendor's change carrying it made, such as a close where the vendor cannot delete. `context.setLink(item, id)` writes the vendor's id onto a row the vendor just made, retrying once if the row moved since, and throws `LinkTaken` for a value another row carries; the example takes that as a refusal. It keeps the id with the row's agreement before it writes, so after a create that got no answer the kit can tell that id from another link the row holds. It never overwrites a link a row holds, whichever way the write arrives, unless the row's agreement already names that link as the connector's: it throws `LinkTaken`, and the row keeps its link. The kit carries nothing by a link whose agreement does not name it, and raises a condition that says so; where the agreement kept no id to be written, the condition says its provenance is unknown and that the connector leaves it alone. Resolving means the vendor took the change, or there was nothing to send: the kit then takes the carried values as the vendor's, so a handler never resolves after a write the vendor did not take, and never answers one with only a condition. A change the vendor did not take is thrown as `Unreachable` or `Refused`, and either way nothing is agreed, the row keeps the person's values over the vendor's next read, the run goes on, and a condition says why until the change lands; a change the vendor is not to take at all is thrown as `Declined`:
  - **`Unreachable`**, for an answer that can pass by itself, such as a rate limit, a server error, a timeout or no answer: the change is sent again next run. Give it a message naming the row; where many rows can wait on one part of the vendor, such as one account, pass that part as `scope` and a message naming it instead, and the changes waiting on one scope raise one condition between them, saying how many wait.
  - **`Refused`**, for an answer that will not change by sending again, such as a value the vendor rejects or a row the account may not change, with the vendor's reason as its message: the kit names the row beside it. The same change is not sent again, so the vendor is not asked the same thing every run; once the row changes in Marfa, by a person or by the vendor's own read, what differs is sent. A refused edit is sent again once a carried field changes, a cleared one included; a refused trash, which carries no field, only once the row is restored. A purge, which cannot change, is asked again a day after its refusal, and its condition stands meanwhile; one refused seven times is given up, with a condition saying the vendor may still hold the row. A purge waiting to be carried is kept as the row's own fields and its link, and the kit keeps at most 128 KiB of them, giving up the ones refused most first with a condition, so they cannot crowd out the rest of the connector's state. While a refusal stands, `change.refused` marks it: a refused write made nothing, so a create sent after one takes an idempotency key of its own from it, where a key kept across a lost answer would have the vendor answer the refusal again. The reason kept with the row is cut to 200 bytes, and dropped where the row's agreement has no room for it beside the refusal; where it has no room even for the refusal's mark, which the instance's cap on one agreement decides, nothing is remembered, and the change is sent again each run, as its condition says.

  - **`Declined`**, where the vendor is not to be asked at all, such as an edit to something another person wrote there, with a message naming the row: the fields the change carried are put back to what was agreed, the row's state stays as Marfa has it, the message is raised as a condition, and nothing is tried again until the row changes again.

  Any change may carry `change.unagreed`, the read-only fields the row holds otherwise than was agreed with the vendor, where putting them back failed: none of them is the vendor's, so a decision taken on one waits.

  Any change may also carry `change.placement`: for each connection type the vendor holds read only, such as the repository an issue sits in, the rows the agreed connections name, as the vendor was told of them. It says where the row sits as agreed with the vendor, never what a person drew since, so a decision about where to write or whether to wait is taken on it rather than on the row's own text.

  What stops every change, such as a vendor refusing the token, is thrown as any other error and fails the run; the change waits for the next. The example sends a 429, a 5xx or no answer as `Unreachable` and any other refusal as `Refused`. Where a create is sent again after a try whose answer was lost, the vendor answers with what that try made, from the values the row held then, so the example links the row to that item first and then sends what the row holds now over it, so a refused update leaves a linked row and the next change goes out as an edit.

- **`readOnly`**, optional, on each type: fields the vendor holds that are never carried back. Marfa mirrors them: a change made to one in Marfa is put back on the next run, from what the connector last wrote, and the run names the field. Every field is read-only for a connector without `onChange`, or for a type its `carries(env)` leaves out, so any kind can run read only; and the link is read-only for every type. It may also name connection types from the type's rows that the vendor cannot change that way, such as the repository an issue sits in: Marfa mirrors them as it does a read-only kind's, putting back a change and naming it, but a create, and `remake`, are handed them in `change.connections`, since they say where the row goes. A create waits until the vendor has been told about each row they name, within the same run where that row is made in it, and the run names a create still waiting.
- **`revive`**, optional, on each type: a row in the bin comes back when the vendor changes it, once its trash has reached the vendor, and the run names it; a change only in a `derived` field is not such a change. It comes back as the vendor has it, its close among the fields, where Marfa had not changed them. A trash still waiting to be carried is never undone this way. Carrying the trash must answer the vendor's entry, or the vendor's own close reads as a change and brings the row straight back.
- **`derived`**, optional, on each type: read-only fields that say where a row sits, not what happened to it, such as its container's visibility. A change in one is never the vendor's activity: it brings no trashed row back, and a field an agreement never held is no change. A row in the bin is left alone, so it takes the value when it comes back.

Every entry `run` hands to `upsert` should carry `changed_at`, when the vendor last changed it: it is what the conflict rule reads, and a vendor naming no time loses every conflict.

- **`remake(change, context)`**, optional: makes a restored row again at a vendor that no longer has it, links the row to what it made, and answers whether it did. It is asked for every `restored` change before the vendor is read; a row the vendor still has answers `false` and is carried by `onChange` after the read. It answers `true` only once the vendor has made the row and it is linked: a remake the vendor did not take throws `Unreachable`, `Refused` or `Declined` as `onChange` does, and is asked again by the same rule. Where a remake failed before, `change.attempted` says when it was first asked, so what it made then can be found. The example asks the vendor for the item and makes it again on a 404.

A row Marfa wrote as a conflicted copy is never a create. When another writer's stale `PATCH` with `conflict=auto` collides with an edit on a `keep_both_copies` property, such as the `body` of a `core.task`, Marfa keeps the losing value in a new row of the same type, under the original's source, without its link, tagged `conflicted-copy` and joined to the original by a `derived-from` edge. That row has no link, like one a person made, but it holds a conflict for a person to resolve, so the kit does not offer it to `onChange` and nothing reaches the vendor. The kit leaves the copy in Marfa, unchanged, and raises one condition per copy, `conflicted-copy:<id>`, that names the copy. The condition stands, and the kit looks again each run, until the person puts the copy in the bin or removes its `conflicted-copy` tag, after which a copy still in Marfa is carried as a create like any other row. The kit asks Marfa for the tags of a row only when it would otherwise send a create the kit has not sent before.

How a run goes: the log is read, and each row it names is compared with what the two sides last agreed on; what differs is recorded as waiting, from when it was first seen, before the log's cursor moves past it, so a run that fails, or a process that stops, loses nothing still to carry. Creates are carried, and restored rows offered to `remake`; `run` pulls and writes what the vendor had; the rest of what waits is carried; the state is kept, and then the run is reported. A create goes before the vendor is read, because a run that failed between the vendor's answer and the link would otherwise read the vendor's copy first and create the row's twin. The kit records a create before sending it; where one was sent and no link came back, `change.attempted` says when it was first sent, so a connector whose vendor takes no idempotency key can look for what it made before making another. Where a create made the vendor's object and linked the row but the run then failed, nothing was agreed for the row's fields, so the next change is an update with every field the vendor has not since sent back in `changed`, and `change.made` says when the create was first sent; a connector whose create took fields sends one of them only if it differs from the vendor's object. The report's `pushed` counts every change carried, landed or abandoned; `own` counts the log's frames showing a row as the connector last left it, which are its own writes; `conflicts` counts each row where a field was decided by the later change.

A trash in Marfa wins over the vendor: a trashed row is never written, unless its type revives, and the trash is carried. An archive in Marfa touches no field and travels beside whatever the vendor sends. A restore is carried as a restore, made again at a vendor that no longer has the row; where a trash deletes at the vendor, a change there after the restore means the vendor has the row again, and where it only closes, as for a type that revives, the restore still reopens it. A row the vendor deleted is archived, and a person's restore of it since is not undone by the vendor's next word. A purge is carried once, kept on the instance until it lands, so a run that fails first loses none; one the log no longer holds, as after a long time offline, is remembered but not carried; the example sends the trash's delete again, which a vendor that took it answers as already done, and which still deletes where a trash and a purge made between two runs reach the connector as the purge alone. A row another row's trash took into the bin, through a connection that cascades, is not the person's trash of it: its trash, its restore and its purge are not carried, and a field changed before it waits for the restore. The instance's `parent-of` is such a connection: a trash of a series in Marfa is carried once, as the trash of the series, and the exceptions it took into the bin are not carried separately; restoring the series brings them back, with only the restore of the series carried. The connection itself stays while the series is in the bin.

For an operation whose exact request must survive a restart, use `context.outbound` inside `onChange` or `remake`. Read `outbound.get(change.item.id)` first. If none is pending, await `outbound.save(change, { request, baseline })` before sending HTTP. Both values must be lossless JSON; keep credentials in settings marked `secret`. The returned intent contains a token and detached copies of the captured change, request, and baseline. A pending request cannot be replaced, and exceeding the state limit refuses the save before HTTP.

Validate a saved request before using it, recover uncertain vendor outcomes using that exact request, and then await `outbound.acknowledge(change.item.id, intent.token, answer)` before returning. Omit `answer` to settle the captured values; otherwise supply the vendor's entry as confirmed. Once acknowledged, the kit settles the captured change without calling the vendor again. It deletes the intent only after Marfa acknowledges the agreement. Newer local edits remain pending. The journal is separate from item agreements, so purging a row cannot erase its pending request. A pending intent is retained on any refusal until it is resolved and acknowledged. Replay checks the current kind and row write authority. A read-only kind, lost ownership, missing row, or missing handler leaves the intent intact and reports why it waits; other kinds can continue. The affected row is withheld from inbound writes and mirror restoration until recovery is authorized again, so newer local values survive. An uncertain create without a known vendor identity withholds inbound entries for its kind. A queued purge also waits while its kind is read only or no longer declared. Restoring write authority resumes the original request; a missing row never establishes authority.

A create or remake whose answer was lost ends by linking its row, so the person's trash or purge of that row before the next run overtakes it. The kit never sends the create again for a row in the bin or gone. Instead, the replay calls `onChange` with the person's change: a `trashed` change with the row as it stands, or a `purged` change once the log has shown the purge, which the kit then remembers until it is settled. Either carries `change.attempted`, and `outbound.get(change.item.id)` returns the pending create or remake. Ask the vendor with the saved request whether that write made anything, delete what it made, and then await `outbound.acknowledge` with the pending intent's token before returning: a create that never reached the vendor needs only the acknowledgment. Use `outbound.advance` to journal the delete; `outbound.save` refuses, since the intent is pending. While the row stays in the bin or gone, later runs hand the trash or purge that delete request. The kit then settles the trash or the purge, not the create, and deletes the intent; a lost acknowledgment is settled the same way on the next run without calling the vendor. A refused, unreachable or declined answer leaves the intent pending, as for any other replay. So does a handler that returns without acknowledging it: the run names it in a condition rather than failing, and withholds the row from inbound writes until the intent is settled. A row restored before the next run gets the original create or remake replayed, with that write's own request and token from `outbound.get`, even where the trash had advanced the intent to a delete: the delete may or may not have landed, so ask the vendor with the create's request whether its object still exists before linking it or making it again. A row restored after its trash settled is a create again, with `change.attempted`, so the vendor's earlier copy can be found. Neither the trash nor the purge carries a link the row holds since the create was sent, which a person may have typed: each carries only the link the pending write's own agreement held, and a create has none. A row another row's trash took into the bin keeps its create waiting, with a condition, until it is restored or purged, and a purge the log no longer holds is not seen, so its create keeps waiting too.

To guard a whole batch, implement `preflight({ purges, trashes }, context)`. It runs once before any outbound callback. `purges` holds every observed purge, including cascade observations, queued retries that are not due, journaled purge operations, and each purge that overtakes a pending create or remake, with its `change.attempted`. The purge snapshots retain properties needed to judge ownership and are not dropped to fit the state limit. `trashes` holds every trash the run would send, whether carried, replayed from the journal, or sent in place of a pending create or remake it overtakes, each with the row as `onChange` would see it, `change.placement` included. A trash another row's cascade made is not among them, since it is never carried; neither is a trash the vendor refused that still stands, a journaled trash the vendor already answered, or a journaled trash whose replay waits for the reasons above. `purges` differs: it holds every journaled purge, including one the vendor already answered or whose replay waits. A row trashed and then purged is among the purges alone, and a row restored before its trash was carried is in neither. Count what you need, such as the trashes in each container, read a complete vendor inventory if needed, count any vendor-side cascades, and throw to hold the batch. Marfa's own folders hold a removal only when it exceeds both a number of files and a fraction of the folder, which suits a connector too, so that a small container can still be emptied. Do not mutate the vendor in this hook.

A held batch fails the run before the vendor is read. Nothing is carried, not even the changes the hold does not concern, and the vendor's own changes wait too, because creates and remakes go before the vendor read so that a run never reads a twin of a row it is still making. Everything waiting is offered to `preflight` again on the next run, so the hold stands until the person restores the trashed rows in Marfa or the connector's rule lets the batch through. A trash that `preflight` did not see is sent only after a later run's `preflight` sees it. This covers a row trashed after the run read it, and a journaled trash whose replay could resume only after the hook ran, which waits as described above. The kit refuses outbound work on an incomplete watch; a connector with this hook also refuses when an expired cursor prevents it from proving the complete purge inventory.

A connector without `onChange` reads the log too: a change made in Marfa to a field it mirrors is put back from what it last wrote, on the next run, and the run names the field.

## Receiving webhooks

A vendor that posts webhooks, such as GitHub, can tell the connector what changed rather than wait for its schedule. The instance stores each delivery as it arrived and never reads it; the connector declares how to read one:

```ts
inbound: {
  // The vendor's signature over the body exactly as it arrived.
  verify: (delivery, env) =>
    verifyHmac({
      secret: env.example_webhook_secret,
      body: delivery.body,
      signature: delivery.header("X-Signature"),
    }),
  // What the delivery says changed, as ids `run` can fetch.
  hints: (delivery) => [
    {
      type: "example.item",
      id: String(JSON.parse(new TextDecoder().decode(delivery.body)).id),
    },
  ],
},
```

- **`verify`** answers whether a delivery came from the vendor. `verifyHmac` from the kit compares an HMAC in constant time: `prefix` for a header such as GitHub's `sha256=…`, `encoding: "base64"` for a vendor that signs in base64. The secret is declared in `settings` with `secret: true`, so it never reaches a log line. A delivery that fails, or whose `verify` throws, is marked rejected for good and changes nothing, and the run says how many with a condition, which usually means the secret differs from the one the vendor signs with. Keep `verify` to the delivery and the environment: a check that reaches the network can fail for a passing reason and reject a genuine delivery. It is handed a signal that aborts on a stop or after ten seconds; a check still running then leaves its delivery waiting for a later run, with a condition, and the deliveries behind it are taken.
- **`hints`** answers what the delivery says changed, as the type and id of each thing `run` fetches, or `"everything"`. A `hints` that throws, as the example does on a body that is not JSON, means everything, and the run says how many with a condition; neither error's text is kept, since it can quote the body. A delivery is a hint, never the vendor's state: the vendor may send them out of order, twice, or not at all, so `run` always fetches what the hint names and writes that.
- **`run`** reads `context.hints`. It is `undefined` on a scheduled run, which reads the vendor whole, and on a run whose deliveries asked for everything; otherwise it is, by type, the ids the deliveries named, which may be empty, and the run fetches only those and leaves any cursor into the vendor, such as a sync token, where it was, since the rest was not read. Both write through `upsert` and `archive`, so a delivery and the schedule reach a row the same way.
- A run the deliveries started clears no condition, having checked only part, and reports those that stand.
- A connector with `onChange` is handed, beside what the deliveries named, the links of rows with a change in Marfa still to carry, so the run reads what it will write over. A field changed in Marfa is carried only over a row whose entry the run read; the rest wait for the next run that reads them, and the scheduled run reads the vendor whole. A run for deliveries archives only what it was handed, since the rest of the vendor was not read, and with more than two hundred rows waiting it reads the vendor whole.

How deliveries are taken:

- Every run first collects what waits at the connector's inbound endpoints, up to five hundred, fetching each body to verify it. A body that cannot be fetched leaves its delivery waiting for a later run, with a condition, and the rest are taken. A verified delivery that repeats one already processed, or one verified earlier in the same collection, by the header the inbound endpoint names, is marked a duplicate.
- A delivery is marked processed once the run that took it ends without error. A write the run held does not keep it waiting, since the next scheduled run reads the vendor whole and writes it again; a run that fails leaves it waiting for the next.
- A scheduled run that cannot read the deliveries or the inbound endpoints says so with a condition and still reads the vendor whole.
- With `--every`, the kit looks between scheduled runs, every ten seconds or as often as `--look-every` says: for a waiting delivery, for a change in Marfa its vendor has not had, where the connector has `onChange`, and for a change in Marfa to a field it mirrors, which it reads from the log and tells from its own writes. Any of them starts a run for it at once, so a change made in Marfa reaches the vendor, or is put back, within a look rather than at the next schedule. A run that fails, or whose deliveries could not be marked, leaves what waits for the scheduled run rather than trying again at every look. The schedule stays the safety net, since a vendor does not promise to deliver: GitHub does not retry a failed delivery. `--look-every` is refused for a connector that neither receives webhooks nor carries changes back.
- Each run's report counts the deliveries it processed, rejected and marked duplicate.

The address comes from the instance, never from the kit. With the connector registered, make an inbound endpoint with its own key or a key holding `connectors.manage`:

```bash
marfa connectors endpoints create <connector-id> --label <vendor> --duplicate-header <header>
```

The answer carries the address in full this once, as `path` and as `url`, the address the binary reached joined to it; later reads show only its last four characters. Give the vendor the instance's public address with that path, and the secret it signs with. `--duplicate-header` names the header a vendor repeats on a redelivery, such as `X-GitHub-Delivery`. A scheduled run whose registration holds no live endpoint says how to make one. `marfa connectors endpoints retire <connector-id> <endpoint-id>` stops an address answering. `marfa connectors deliveries list <connector-id>` shows what waits, with the connector's own key only: a management key is refused, as on every read of the connector's data.

## The key

A connector starts from the key its connector host mints for it, never one minted by hand. Install the connector's plugin, link a host and assign the connector to it, as [Run a plugin's connector on a connector host](https://docs.marfa.so/use/run-a-plugin-connector) says:

```bash
marfa plugins install connectors/<name>/plugin
marfa hosts add "<machine>"
marfa plugins assign <name> --host "<machine>"
```

The host program redeems the one-time link `marfa hosts add` prints (`POST /connector-hosts/redeem`) and mints the connector's key (`POST /connector-hosts/self/connectors/<name>/key`), as [Build a connector host](https://docs.marfa.so/build/connector-host) says, and starts the connector with it as `MARFA_API_KEY`. The key holds the connector's source as its own, write on the type of each of its kinds and on each connection type the plugin names, and nothing else: no permission, no metadata entry, no claim, and the feed as its default tier. Each mint revokes the key minted before, and removing the plugin revokes it.

The kit reads the key back on every start (`GET /keys/current`), before it checks a type or writes a row, and names the key and what to change when it refuses one. The refusal is the registration's failed run, except that a key an app made is refused before the connector registers, so it is only logged. The process then exits with code 3. It refuses a key that:

- holds any permission, including management permissions and `schema.write`;
- holds any level on a type other than the connector's own, or on a connection other than the ones it declares (the key names the edge type, so `parent-of` for a declared `child-of`), or on an extension or profile field, or any enforcement override;
- holds any metadata entry, such as `types` or `edge_types`, which a connector that registers nothing never needs;
- does not hold write on each of the connector's own types and connections;
- is one an app made;
- writes under a source that is not the connector's, or claims any source;
- has a default tier other than the feed.

A key of that shape that no host minted, such as one a self-registered connector held before its plugin was installed, starts, but Marfa gives the settings only to the key a host minted under the plugin's connector, so a connector that declares settings stops with exit code 3, saying to start it with the key its host mints.

### When the installed plugin's types differ from the build

Installing the connector's plugin (`marfa plugins install <name>`) registers its types and connection types in one write; the kit registers and changes none, and the key holds no metadata entry for it. On every start, and before each scheduled run while the connector writes without something, the kit reads each type it declares from the instance and compares it with the one this build carries.

- **A field on the instance that the connector does not declare** is kept, and is no difference: an operator or another version of the plugin added it. A field the instance requires that the connector does not declare is a difference, as below.
- **A label, description or display hints that differ** are no difference: nothing the connector writes depends on them.
- **An optional field or table the connector declares that the installed type lacks**, as when a build is newer than the installed plugin, starts the connector without them: it writes nothing under them, so the rows keep whatever they hold there, and each run raises one condition, `plugin-types`, that begins with the fix: `marfa plugins install <name>` with the plugin's newer version, which may only add to its types. Under `--every`, each scheduled run reads the types again, so updating the plugin lifts this without a restart, and a check that finds any other difference stops the process with exit code 1, as at start.
- **Any other difference stops the start**, with the one message that the installed plugin's types differ from this build, naming each difference and the update: a type that is not installed, a changed link field or parent, a field made required or given another shape, a required field the instance lacks or the connector does not declare, and the link field, `blob_ref` or `mime_type` missing, since the connector cannot write its rows without them. A connection type that is not installed, or that differs in cardinality, delete behavior, reverse name, direction or an endpoint list that does not take every type the connector writes, stops it the same way; an installed endpoint list that is wider, or holds `*`, is no difference, since a plugin installs the widest shape its connector takes. The kit sends no `POST /types`, `PUT /types`, `POST /edge-types` or `PUT /edge-types` in any case.

## Run it

The environment is `MARFA_API_URL`, `MARFA_API_KEY` and, optionally, the [telemetry](#telemetry) settings; the kit reads nothing else from it. Every setting `settings` declares comes from Marfa, at the start of every run (`GET /connectors/{id}/settings`), so the owner changes one with `marfa plugins settings <name> --set <setting>=<value>` or `marfa plugins secret <name> <setting>` and the next run uses it, with no restart. The connector keeps no file: its state is on the instance.

- **`node dist/main.js --once`**: one run, then exit, for launchd, cron or a scheduled container, which exits as [Exit codes](#exit-codes) says. A run cut short by SIGTERM or SIGINT is not reported, since a run's outcome is only succeeded or failed: the log says it stopped, and what it had already written and agreed is kept, so the next run carries on from it. The connector's state is saved before the run is reported, and a save the server refuses, such as one past its 512 KiB cap on the state, fails the run, so a run never reports success while its progress stands still. The private state holds the connector's own values, the log's cursor, and the purges still to carry, each kept until it lands at the vendor. Standing conditions are saved separately as the source's explicit `problems` snapshot, with at most two hundred entries and each message cut to 500 UTF-16 code units. Checkpoint and final saves commit both snapshots together. Registration and manager reads expose current problems; a heartbeat or successful report leaves them standing.
- **`node dist/main.js --every 15m`**: a long-lived process. Runs never overlap, and the heartbeat has its own one-minute timer. A failed run is reported, and the next waits twice as long, up to eight intervals, or as long as a refusal's `Retry-After` names if longer. A run that failed because Marfa did not answer is asked about instead: the connector checks Marfa every 15 seconds or the interval if shorter, a little spread so connectors do not arrive together, and runs again once it answers; if that run fails for Marfa again too, the backoff applies, until a run succeeds or fails for another cause, which re-arms the quick retry. A key the server refuses, one narrowed so it no longer writes the connector's types, or one widened past what the kit accepts, which it reads back before each run, stops the process with exit code 3, and a setting changed to a value the connector cannot use stops it with exit code 4. Exit code 2 is for an address that cannot be used: a redirect or a malformed URL. A host that is not found, an untrusted or expired certificate or a refused TLS handshake may mend, as when the connector starts before the network is up, so at start it is tried again as a Marfa that does not answer is, and once running it is waited out, each with a warning that names `MARFA_API_URL` and the cause; under `--once` it exits with code 1. A registration the server no longer holds, which any door can say, the settings door included once it has answered for the registration, is made again, and so is the check of the connector's types after one of them is deleted from the instance while it runs, which stops the process with exit code 1 naming the type unless the plugin has been installed again; a connector running without fields the installed type lacks checks its types again before each scheduled run, and a second loss within five minutes stops it with exit code 1. The heartbeat is sent every minute, apart from the hold's renewals, which are spaced by the instance's window. SIGTERM stops it cleanly. A connector that receives webhooks or carries changes back also looks between runs, every ten seconds unless `--every 15m --look-every 30s` says otherwise.

- **`node dist/main.js --setup`**: once, by hand, for a connector with `setup`, which registers it with its vendor. It is handed `listen(page, options)`, which serves the page at an unguessable local address the log names, for the person to open in a browser, and waits for the vendor's redirect to its `callback`; a page that must name that address, such as a GitHub App manifest's `redirect_url`, is given as a function of it; the browser the vendor sends back is held at the callback, which answers once, until setup ends and it is told whether setup succeeded, or until the listen's `onward(address)`, called once the redirect has arrived, sends it on, such as to the page where the vendor asks for the next step; `endpoint()`, which makes the connector's own inbound endpoint and answers its address this once; and `secret`. When the browser is on another machine, the vendor's redirect cannot reach the callback. A vendor whose sign-in can begin away from the local page, such as Google's consent screen, can take the redirect by paste instead: `listen(page, { paste: (callback) => address })` names the address a browser on another machine opens to begin, and the log then says to open it there, paste the address the browser ended on into the terminal and press Enter. A pasted line takes the place of the redirect: whichever arrives first is used, and the other is ignored. A pasted line must be a web address whose path is the callback's; anything else is not used and draws one warning that never repeats it. Setup reads the terminal only while such a `listen` waits, and never for a `listen` without `paste`, such as GitHub's, whose page is served only on this machine. `onward(address)`, after a paste, logs the address for the person to open in place of redirecting a browser. What it answers, each by the name of a setting the connector declares, it prints on standard output as the commands that set it, `marfa plugins settings <name> --set <setting>=<value>` for a value and `printf '%s' <value> | marfa plugins secret <name> <setting>` for a secret, which `marfa plugins secret` reads from standard input; the owner runs them where `marfa` is signed in as the owner, such as by piping them to `sh`. They hold the secrets in full, so keep them out of a file or a shared terminal. Nothing is written to a file. If setup fails, it prints nothing, and every endpoint it made is retired, or named with the command to retire it by hand where the instance would not. Each inbound endpoint setup makes is labeled with the connector's label for it and when it was set up, which tells it apart in `marfa connectors endpoints list <connector-id>`, and setup names the id of each; once the vendor posts to the new one, retire any it replaces with `marfa connectors endpoints retire <connector-id> <endpoint-id>`, since a registration holds at most ten live inbound endpoints. The kit never logs what setup answers; setup passes anything it logs itself through `secret` first. It reads the settings set so far from Marfa, and needs none of them, but a secret shorter than eight characters stops it with exit code 4, as it stops a run. It leaves the registration's read-only types as a connector running beside it set them.

One process runs a connector at a time. Each run is made under a hold on the connector's registration, renewed a third of the instance's window apart, beside the heartbeat and let go when the process ends; a second process under the same key waits under `--every`, trying again a second after the hold would lapse, but no sooner than half a minute and no later than its next interval, so a process that took over from one stopped uncleanly runs within minutes, and one standing by beside a live process asks every few minutes; under `--once` it exits without running. Each says until when it is held. A run whose hold can no longer be trusted, because another process took it, it lapsed, or five sixths of the window the instance names (`ttl_seconds`) passed since a renewal landed, stops before its next carry and keeps nothing more of what it read; the next run reads it again. The instance refuses a write to the connector's state or agreements from any process but the holder.

### Exit codes

The process exits with a code that tells its host what to do next:

| Code | Cause                                                                                                                                | What mends it                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| `0`  | It stopped cleanly, or a `--once` run succeeded.                                                                                     | Nothing.                           |
| `1`  | Any other failure, such as a failed run, a Marfa that did not answer, or a host not found or certificate refused at `MARFA_API_URL`. | Starting again, after a backoff.   |
| `2`  | The connector's definition or command line is wrong, or `MARFA_API_URL` is malformed or redirected.                                  | A change to the code or the setup. |
| `3`  | Marfa refused the key (`401`, or `403` on the connector's own doors), or the kit refused it.                                         | A key its host mints again.        |
| `4`  | A required setting is not set, or a value is not one the connector can use.                                                          | The owner changing its settings.   |

### Telemetry

A connector can send its logs and a trace of each run, which carries the error of a failed run, to an OpenTelemetry collector over OTLP/HTTP. Telemetry is off by default: until `OTEL_EXPORTER_OTLP_ENDPOINT` is set, the kit sends nothing of its own, loads no OpenTelemetry code, opens no connection, and writes the same log lines. A failed run reaches its owner through Marfa, as a run recorded with its error, which `marfa attention` lists. The settings are the ones Marfa's server reads, so one set of values serves both.

| Setting                                                                | Meaning                                                                                                                                | Default                                   |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                                          | The base URL of the collector. Setting it turns telemetry on: traces are posted to `v1/traces` and logs to `v1/logs` under it.         | Unset, so telemetry is off                |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`                                   | The URL traces are posted to, used as written. It needs `OTEL_EXPORTER_OTLP_ENDPOINT` set too.                                         | `v1/traces` under the endpoint            |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`                                     | The URL logs are posted to, used as written. It needs `OTEL_EXPORTER_OTLP_ENDPOINT` set too.                                           | `v1/logs` under the endpoint              |
| `OTEL_EXPORTER_OTLP_HEADERS`                                           | The headers sent with every export, such as the collector's API key, as comma-separated `key=value` pairs with percent-encoded values. | None                                      |
| `OTEL_EXPORTER_OTLP_TRACES_HEADERS`, `OTEL_EXPORTER_OTLP_LOGS_HEADERS` | The headers sent with one signal's exports. They override `OTEL_EXPORTER_OTLP_HEADERS`.                                                | None                                      |
| `OTEL_SERVICE_NAME`                                                    | The `service.name` on everything sent.                                                                                                 | The connector's `name`                    |
| `MARFA_OTEL_SAMPLE_RATIO`                                              | The share of run traces sent, from 0 to 1. A failed run's trace is always sent.                                                        | `1`, where the server's default is `0.05` |

What a connector sends:

- **A trace for each run**, of one span named `connector run`, with the attributes `marfa.connector.trigger` (`schedule` or `look`) and `marfa.connector.outcome` (`succeeded`, `failed` or `stopped`). A failed run's span has an error status and an `exception` event with the error's type, message and stack.
- **A log record for each log line**, with its level as `INFO`, `WARN` or `ERROR`. A line written during a run carries that run's trace and span IDs.
- **The connector's name on everything**, as the resource attributes `service.name` (unless `OTEL_SERVICE_NAME` replaces it) and `marfa.connector.name`, which is always the connector's `name`, beside `deployment.environment`, which is `production`, as the server labels its own.

Everything is redacted as it leaves the process, by the same rule as the log: `MARFA_API_KEY`, each setting `settings` declares as a `secret` or Marfa holds as one, each secret kept with `secret` during a run, and their URL-encoded spellings become `[redacted]`. A header value of eight characters or more is treated as a secret too, so the collector's API key never reaches the log. A connector should not put an item's content in an error, since a message that quotes it as plain prose cannot be told from the error's own words.

Telemetry never fails or holds up a run. An export that takes longer than 1.5 seconds, retries included, is dropped, and the first export that fails is warned of once. When the process ends, including on SIGTERM or SIGINT, it sends what is waiting and gives up after at most 3 seconds. Startup failures found before telemetry starts, including a missing `MARFA_API_URL` or `MARFA_API_KEY`, are logged only. A malformed setting, or a signal's own endpoint without `OTEL_EXPORTER_OTLP_ENDPOINT`, stops the start with exit code 2, naming the setting and never its value, as the server refuses one.

### launchd

`launchd.plist.example` runs the connector `--once` once at load and then every fifteen minutes (`RunAtLoad` and `StartInterval`), so the first run comes when `launchctl bootstrap` loads it, not one interval later. Copy it to `~/Library/LaunchAgents/`, give it a label and the real paths, and load it with `launchctl bootstrap gui/$(id -u) <plist>`. Its `ProgramArguments` start the connector under a secrets tool, so the key never sits in the plist; the vendor's token is a setting Marfa holds.

Under `--once` the connector takes the deliveries that wait at its inbound endpoints only when it runs, so a webhook is acted on at the next run, within fifteen minutes. Run it `--every` to act on one within seconds.

### A container

`Dockerfile` builds an image that runs one connector `--every 15m`. It copies only the workspace's manifests and the kit's and the connector's sources, so no other file in the checkout reaches the image. Build it from the repository root; its frozen install fetches the published client without a server checkout:

```bash
docker build -f template/Dockerfile --build-arg CONNECTOR=<name> -t <name> .
```

Pass `MARFA_API_URL` and `MARFA_API_KEY` with `-e`. The container needs no volume: a new one picks up where the last left off, from the state kept on the instance.

When Reader or another vendor returns a retry deadline, throw `new Unreachable(message, { retryAt: deadline })` with an ISO timestamp. The kit persists the deadline before continuing and pauses all vendor callbacks, including preflight and the reader, until it expires. The deadline also works when a baseline read is throttled before an outbound intent exists. To resume the same callback with its in-memory page cache, await `context.waitUntil(deadline)` instead. The reader, its scoped contexts, and watch callbacks share this durable wait. It saves only acknowledged state, keeps draft state in memory, and resumes only after the deadline has passed and clearing it has been acknowledged. Cancellation or a lost state acknowledgment ends the callback without resuming vendor requests.

Only when the vendor response proves the request did not apply, such as a documented HTTP 429 rejection, add `requestNotApplied: true` to that `Unreachable` error. Recovery exposes this evidence on the saved intent. Before retrying the exact request, await `context.outbound.prepareRetry(itemId, token)` to consume the evidence durably. A crash or lost acknowledgment after this reset leaves the request uncertain again. A timeout or a throttled readback provides no such evidence.

For a multi-step operation, prove the current step completed, then await `context.outbound.advance(itemId, token, { request, baseline })` before sending the next request. It returns a new token and preserves the original captured change. A lost replacement acknowledgment blocks sending until recovery reads the durable phase. In the reader, `context.pendingOutbound()` returns detached snapshots so inbound admission can withhold identities still being created.
