# @withmarfa/connector

Reference for developers who build a connector on the kit. To start a connector, follow the [template's README](../template/README.md). The exported types and their comments in [`src/define.ts`](./src/define.ts) describe every option; this page says what the kit does with them. The rules the repository is worked under are in [`AGENTS.md`](../AGENTS.md).

## Package

The package is private to the workspace and ships its built `dist/` only. It has four entry points:

| Import                          | Holds                                                                                                                                                                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@withmarfa/connector`          | `defineConnector`, `main`, `exitCode`, the errors `Unreachable`, `Refused`, `Declined`, `LinkTaken` and `SettingsRefused`, `verifyHmac`, `rowId`, `carriedTypes`, `edgeTypesOf`, `shippedConnection` and the types of the definition. |
| `@withmarfa/connector/markdown` | `htmlToMarkdown`, `markdownToHtml`, `NotConvertible`, `withinLimits`.                                                                                                                                                                 |
| `@withmarfa/connector/pictures` | `fetchPicture`.                                                                                                                                                                                                                       |
| `@withmarfa/connector/network`  | `privateHostSet` and the address guard `fetchPicture` uses.                                                                                                                                                                           |

A connector imports only the package. The one exception is `kit/test/scripted-server.js`, a test helper that nothing built into the connector reaches.

## What the kit does

A connector does four things, and the kit carries all but the vendor's side of each.

1. **Registers.** On every start the kit registers the connector with the instance, reads the key back and refuses a wrong one ([The key](#the-key)), reads the settings ([Settings](#settings)), and checks each type and connection type the connector declares against the instance's ([Installed types](#installed-types)). Installing the connector's plugin registers the types; the kit registers none.
2. **Reads.** `run` reads the vendor and hands what it found to `upsert` and what the vendor deleted to `archive`. The kit compares them with the rows already written and writes only what changed ([Reading](#reading)).
3. **Delivers.** A connector that also carries changes made in Marfa back to its vendor declares `link_field` on its type and an `onChange` ([Carrying changes back](#carrying-changes-back)).
4. **Reports.** The kit heartbeats, keeps the connector's state and reports each run to the instance as succeeded or failed, with a summary. A problem that lasts but lets the run go on is `log.condition`. An error thrown from `run` fails the run: the process exits with code 1 under `--once`, or with code 4 for a `SettingsRefused` ([Exit codes](#exit-codes)).

## The definition

`src/definition.ts` exports `connector()`, built with `defineConnector`. It reads no `process.env`.

| Member                                              | Meaning                                                                                                                                                                                                                                                |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`, `title`, `mark`, `maker`, `description`     | The connector and the plugin it is published as. `title`, an Iconify `mark` and `maker` are required for a connector under `connectors/`.                                                                                                              |
| `source`, `sourceName`, `sourceMark`                | The source rows are written under, its name (the system, not the route the data came by and not an account) and a mark from the `simple-icons` or `lucide` set, such as `simple-icons:github`.                                                         |
| `types`                                             | At most ten kinds. Each has a `name` in lowercase snake case, a `direction` (`in`, `out` or `both`), a `type` (the type definition), the `fields` the vendor holds and optionally `readOnly`, `derived`, `retired`, `revive`, `archived` and `policy`. |
| `connections`, `retired`                            | Connection types between the connector's own rows, and connections a row once wrote and no longer does.                                                                                                                                                |
| `settings`, `signIn`, `checkEnv`                    | The settings the connector reads, how Marfa signs it in to its service, and a check that refuses settings the connector can tell are wrong on sight.                                                                                                   |
| `run`, `onChange`, `remake`, `preflight`, `carries` | The vendor read and the two-way hooks.                                                                                                                                                                                                                 |
| `inbound`, `setup`, `readme`                        | Webhooks, one-time setup with the vendor, and the path of the connector's own README.                                                                                                                                                                  |

- A connector declares each type in its widest shape, because the key a host mints writes only the types of its kinds. A definition that changes with a setting takes the settings as `connector(settings)`. `main.ts` hands `connector` itself to `main`, which builds it again from the settings Marfa holds at the start of every run. The definition exports `widest`, the settings that give it its widest shape, which the generator builds it from.
- A setting has a `name` matching `^[a-z][a-z0-9_]*$` (at most 64 characters), a `label` of 1 to 100 characters, a `kind` of `text`, `number`, `boolean` or `choice`, and where they apply `secret` (text only, never with a `default`), `default`, `required` and `choices` (for `choice` only).
- A type whose rows read as a core type, such as a task, names that core type as its `parent` and adds only the vendor's own fields. `run` then writes the core type's fields under the core type's names.
- A field named as a type's `body_field` holds Markdown ([Converting content](#converting-content)).
- `retired` on a kind lists properties an earlier version wrote and this one does not: the next write of a row removes them. List a name the type no longer declares for one release, then delete it. A name the type still declares, because a published plugin never narrows, stays for as long as the type declares it and the connector writes none of it.
- `archived(properties)` on a kind says whether the vendor holds the row archived, kept and not gone. An entry that says so leaves an archived row archived; any other entry brings back a row the connector archived. It archives nothing: follow the upsert with `archive`.
- `policy(item, entry, archiving)` on a kind returns a `RowPolicy`. `owned: false` leaves the row and its agreement alone. `fields` sets each field to `mirror` (local edits put back), `sync` (carried) or `observe` (kept, never carried and no work scheduled). `firstAgreement` is `preserve` (divergent values are scheduled) or `hold` (missing fields are seeded and existing values kept). `adopt`, given with an entry only, makes the row's state as it stands the agreed one. The link always stays mirrored.
- A connector that signs in to Google declares `signIn: googleSignIn(scopes)` from `@withmarfa/google`. The generator writes it as the manifest's `connector.sign_in`: the scopes to ask for and the names of three declared settings, the client ID, the client secret and the token, the last two secrets. The owner sets the client and runs `marfa plugins sign-in <name>`, and Marfa keeps the token it gets as the third setting. That setting is not `required`, since it has no value until the owner signs in. `connectGoogle` throws `SettingsRefused` when it is missing or Google refuses it, so the process exits with code 4.

## The key

A connector starts from the key its connector host mints for it, never one minted by hand ([the template's README](../template/README.md#run-it-under-a-host) has the commands). The key holds the connector's source as its own, write on the type of each of its kinds and on each connection type the plugin names, and nothing else: no permission, no metadata entry and no claim. Each mint revokes the key minted before, and removing the plugin revokes it.

The kit reads the key back on every start (`GET /keys/current`), before it checks a type or writes a row, and names the key and what to change when it refuses one. The refusal is the registration's failed run, except that a key an app made is refused before the connector registers, so it is only logged. The process then exits with code 3. The kit refuses a key that:

- holds any permission, including management permissions and `schema.write`;
- holds any level on a type other than the connector's own, on a connection other than the ones it declares (the key names the edge type, so `parent-of` for a declared `child-of`), on an extension or profile field, or any enforcement override;
- holds any metadata entry, such as `types` or `edge_types`;
- does not hold write on each of the connector's own types and connections;
- is one an app made;
- writes under a source that is not the connector's, or claims any source.

A key of that shape that no host minted starts, but Marfa gives settings only to the key a host minted under the plugin's connector, so a connector that declares settings stops with exit code 3, saying to start it with the key its host mints.

On every start the kit also reads the source (`GET /sources/{source}`) and sets with `PATCH /sources/{source}` only the name and mark the owner has not set, so a name or mark chosen in an app outlasts a restart. If Marfa refuses the call, the kit logs a warning, the connector still starts and syncs, and the next start tries again.

## Installed types

Installing the plugin (`marfa plugins install <name>`) registers its types and connection types in one write. The kit sends no `POST /types`, `PUT /types`, `POST /edge-types` or `PUT /edge-types`. On every start, and before each scheduled run while the connector writes without something, the kit reads each type it declares from the instance and compares it with the one this build carries.

| Difference                                                                                                                                                                                                                                                                                                                                                                                                                  | Result                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A field on the instance that the connector does not declare                                                                                                                                                                                                                                                                                                                                                                 | Kept, and no difference: an operator or another version of the plugin added it. A field the instance requires that the connector does not declare is a difference, as in the last row.                                                                                                                                      |
| A label, description or display hints                                                                                                                                                                                                                                                                                                                                                                                       | No difference.                                                                                                                                                                                                                                                                                                              |
| An optional field or table the connector declares that the installed type lacks, as when a build is newer than the installed plugin                                                                                                                                                                                                                                                                                         | The connector starts without them, writing nothing under them, and each run raises one condition, `plugin-types`, that begins with the fix: `marfa plugins install <name>` with the plugin's newer version. Under `--every`, each scheduled run reads the types again, so updating the plugin lifts this without a restart. |
| An installed connection endpoint list that is wider or holds `*`                                                                                                                                                                                                                                                                                                                                                            | No difference: a plugin installs the widest shape its connector takes.                                                                                                                                                                                                                                                      |
| Anything else: a type that is not installed, a changed link field or parent, a field made required or given another shape, a required field the instance lacks or the connector does not declare, the link field, `blob_ref` or `mime_type` missing; a connection type that is not installed or differs in cardinality, delete behavior, reverse name, direction or an endpoint list that omits a type the connector writes | The start stops with one message naming each difference and the update. A check under `--every` that finds one stops the process with exit code 1.                                                                                                                                                                          |

`written(type)` in a run reports the fields the kit writes now, which changes when the narrowing begins or lifts.

## Settings

Every setting `settings` declares comes from Marfa at the start of every run (`GET /connectors/{id}/settings`), which opens a secret only to the key its connector host minted. The owner changes one with `marfa plugins settings <name> --set <setting>=<value>`, or a secret with `marfa plugins secret <name> <setting>`, which reads it from standard input. The next run uses it, with no restart. The environment holds only `MARFA_API_URL`, `MARFA_API_KEY` and the [telemetry](#telemetry) settings.

- **`env`** in `run`, `onChange` and the other contexts holds each declared setting by name, typed by `kind`: a `boolean` as `true` or `false`, a `number` as a number, a `choice` or `text` as a string. A setting that is not set reads as its `default`, or `undefined` where it has none.
- **A setting that cannot be used** stops the run before it reads the vendor or writes anything, with one condition naming each setting by label and name, never its value, and the process exits with code 4. That covers a `required` setting with no value, a secret Marfa cannot open (as after a restore onto another machine), a value not of its kind, and a secret shorter than eight characters.
- **`checkEnv`** refuses, by throwing, a value the connector can tell is wrong on sight, such as a malformed address. It is asked at the start of every run once the settings are read, and stops the run the same way. Its message must not hold a secret's value.
- **Secrets.** The kit keeps every `secret` setting, and any Marfa holds as one, out of log lines, conditions, run reports, errors and telemetry from the moment it reads them, setup included. A secret that holds a list, such as several addresses, is also kept out part by part, where each part is set apart by whitespace or commas and is at least eight characters long.
- **`secret(value)`**, in `run`, `onChange`, `remake` and `setup`, keeps a value made at run time, such as an installation token, out of every log line, condition and report from then on. A value under eight characters is refused, since it could not be found without redacting ordinary words.

## Mapping

A connector writes each kind as the owner's mapping says. The kit reads it at the start of every run (`GET /plugins/<name>/connector/mapping`). Until the owner saves one, every kind is on, on its own type, at the feed tier.

- **Names.** A connector names its rows by its own types whatever the mapping. The kit writes them as the kind's target type, under the connector's source, finds them again there, follows their changes there and settles their tombstones there.
- **Fields.** Each field of the target is filled as the mapping says: `{"from": <field>}` from a field of the kind, `{"fixed": <value>}` with that value, or `{"template": <text>}` with a [MiniJinja](https://github.com/mitsuhiko/minijinja) template rendered from the kind's fields and nothing else: no file, include, environment or network. A field the kind declares and the entry leaves out reads as nothing, and a name the kind does not declare is an error.
- **Template limits.** A render may do 100,000 units of work, which ends a looping template within milliseconds, and may give at most 100,000 characters. A template that fails, or passes either bound, leaves its field as the row holds it, with a condition naming the field, and the rest of the row is written.
- **Fixed and templated fields** are never carried back: a change made to one in Marfa is put back.
- **Status words.** A word lands on the same word where the target holds it in the same group, else on the target's first word of that group, unless `status_overrides` names one. A change made in Marfa maps back to the kind's word that lands on it, else the kind's first word of the group. A word whose group the other type lacks is not written, or not carried back, with a condition.
- **Unfilled fields.** A target field the mapping does not fill keeps what the owner or another app wrote there. A kind's field that no target field is filled from is left out, and the run says which in one condition. The kind's link field is still written, as a property, where the target names no link of its own, and the kit then finds the kind's rows by their natural key.
- **Connections.** A connection whose edge type does not take an end once its kind is mapped is not written, and the run says so in one condition.
- **A kind that is off** writes, reads and carries nothing, and leaves its rows and their agreements alone. A change made in Marfa waits until it is on again, and the first run after compares its rows whole with what was agreed. A kind whose target type is gone, or is another kind's type, is stopped alone, with a condition.
- **Tiers.** A create names no tier: the server gives each row the tier the owner's mapping chose for its kind, the feed by default. Moving an item between tiers otherwise is a person's or an app's act.
- **When the read fails,** the run applies the mapping the last run kept, says so and keeps it. With none kept, the run does not start. A key that no installed plugin's connector holds (`403` to a connector key, or `404` with `plugin_not_found` or `plugin_connector_not_found`) has no mapping: where no run kept one, its kinds land on their own types and nothing is kept, and where a run kept one, the run does not start rather than write a kind on its own type.
- **Rewrites.** The kit registers the read-only types again, as targets, whenever the mapping's version changes, and carries out each rewrite the owner asks for: it moves the rows each kind wrote on its own type to its target, with their fields as the mapping lands them, clearing the kind's own. A row on a type the kind was mapped onto before moves back with the kind's own fields as the vendor last agreed them, keeping any change made in Marfa that was not yet carried, which the next carry sends to the vendor. It clears the request once every row of every kind it names has moved, and leaves it for a later run otherwise, as it does while one of those kinds is turned off.

## Reading

`run(context)` reads the vendor and writes through the context. A scheduled run reads the vendor whole.

### Writing rows

- **`upsert(type, entries)`**: each entry is a `source_id`, its `properties` and its `occurred_at`. It should also carry `changed_at`, when the vendor last changed it, which the conflict rule reads: a vendor naming no time loses every conflict.
  - Put the vendor account inside the `source_id`, as `<account>:<id>`, only for what that account owns, such as a calendar or a mailbox, so two accounts under one source never share a row. An id the vendor makes unique across accounts, such as a global node ID, needs no account.
  - A property that is absent or `null` is cleared from the row. Every property an entry carries must be among its type's `fields`; an entry carrying another is refused with a condition. A row's other properties are Marfa's own and never touched.
  - `movedFrom` names the link, or the `source_id` where the type names no link, a row was known by before the vendor moved it, newest first. The row is found by them and takes the entry's. Name them for as long as a row may still be held under them, since a row in the bin keeps its old key and a purged one leaves its tombstone there.
  - A row the instance refuses is held with a condition naming it and the instance's reason, and the run goes on; the next run that reads it writes it again. A row a person retyped, to a type the key may not write or to another of the connector's types, cannot be mended by writing it again, so its condition stands for as long as the vendor names the row, and it holds back nothing else.
  - A refusal every write would meet fails the run instead: an instance that does not answer, a key it refuses or one narrowed so it no longer writes the connector's types, the connector's own source refused a create of its type, or every row one call wrote refused alike.
- **What the vendor changed, field by field.** For each row the kit keeps, on the instance, what each side last held, field by field. An entry is written only where the vendor changed something since, and only the fields it changed: an edit made in Marfa to another field stays. A field both sides changed goes to the later change, by the entry's `changed_at` and when the edit was first seen in Marfa, and a tie goes to Marfa; the run names the row and the field that lost. An entry older than what the two sides last agreed on is left unwritten. A row that nothing was agreed for, as after the connector's state was cleared, takes the vendor's value wherever the two differ, and the run says how many.
- **`archive(type, keys)`**: for what the vendor deleted, by natural key, or by the vendor's id where the type names a link. A row is archived, never trashed, and a row a person trashed is never touched. A row archived this way comes back when the vendor sends it again; one a person archived stays archived.
- **`derive(type, keys, values)`** sets a type's `derived` fields on the rows held under these keys, by natural key or the vendor's id as `archive` takes them, where the vendor's answer is not to hand, such as for a container no longer readable. It writes only what differs, never to a row in the bin, and agrees the value so it is no change on the next read.
- **A purge is remembered by the instance.** An entry naming a row a person purged is not written back, however long after and whatever the connector's state, until the vendor changes it after the purge. It then comes back as a new row. The run says how many entries it held back.
- **What a run reads.** Only the rows its entries, the log and the changes waiting name, looked up by link, natural key or id in every state. The type is listed whole only when the log no longer holds the cursor.
- **`file`**, on an entry of a file type: a type whose `parent` is `core.file` or one beneath it, whose `fields` list `blob_ref` and `mime_type`. It gives the vendor's own key for the bytes, such as an etag or asset ID, and `load`, which fetches them, whole or as a stream such as the vendor's response body. A stream is uploaded as it is read, never held whole, and the upload is cut off only when it goes quiet for the request time limit, never for its length. The kit loads and uploads the bytes only when that key differs from the one it last uploaded, in the run that writes the row, and writes the answer as `blob_ref` and `mime_type`; the instance then reads text and image dimensions from them. Bytes the vendor would not give, or a stream that breaks or goes quiet, are a condition, and the row waits. An upload the instance refuses, such as a file of no bytes, holds the row as any refusal does.

### Connections

`connections`, on the connector, and `connections` on an entry, declare kinds of connection between the connector's own rows, such as an issue's sub-issues.

- **Declaration.** Each is an edge type as the plugin's `edge-types/` folder installs it, with both ends constrained to the connector's types, orphaning on delete and requiring no property, since the kit writes none. Installing the plugin registers a custom connection type and the kit only checks it: one that is missing, or that differs beyond endpoint lists the installed type takes wider, stops startup. A custom connection type must orphan, and the kit refuses one that does not.
- **Built-in types.** `attached-to`, `in-collection`, `in-thread`, `references`, `excerpt-of`, `about`, `comments-on` and `parent-of` are checked, never changed. A declaration repeats the instance's own `cascade_on_delete`, declares both ends as the connector's own types and grants only the corresponding edge permissions. `parent-of` cascades on delete. A row attached through `attached-to`, or a comment on a host through `comments-on`, goes into the bin with its hosts (`cascade_on_delete: "with-hosts"`).
- **On an entry,** `connections` names, for each connection type, every row its row points at, by type and by link (or natural key where the type names no link), and an empty list where there is none. A type left out is left as it is. A type never named has nothing agreed, so a change made to it in Marfa is not carried.
- **When they are written.** After the run's rows, so a target made in the same run is found. A target Marfa does not hold yet is connected when it arrives, whether or not the vendor names it again.
- **Carried back.** A connection made or removed in Marfa reaches `onChange` as `change.connections`, the rows at the other end, or is put back where the row's type is read only. A connection a purge took is never carried. One from the connector's row to a row outside the declared ends, such as a person attaching a file to their own note, is theirs and left alone. A change to a connection's properties alone carries nothing.
- **A connection a person moves** to another row, which Marfa keeps as the same edge, is carried, or put back, as a removal and an addition. Where the connector's row is the end that stays, that is one change for that row: the row the connection left among `removed` and the row it reached among `added`. Where the connector's row is the end that moved, which only a `one-to-one` or `one-to-many` connection allows, it is a change for each of the two rows, in no set order.
- **Read-only kinds.** The kit puts back every connection a run found changed in one pass, removing every connection it removes before it draws any, so a target that holds only one connection is free when the row it left draws it again. Marfa names only the row a connection reached, so the kit finds the row it left by reading every agreement the connector keeps, 200 to a request, once in the run. It skips the read when the row the connection reached already agrees with it.
- **After the state is cleared,** where nothing is agreed for a custom connection type, the vendor's set is taken and nothing is carried.
- **`references`, `excerpt-of` and `about`:** only previously agreed or currently requested targets are reconciled. Other references are left alone, including references to another item of the connector's own type.
- **Messages and collections.** A message joins its thread through the instance's own `in-thread`, such as a comment on its issue. The kit writes no `position` on it, so the thread's order is the messages' own time. Since a message is in one thread, one a person put in a thread of their own is left there and the vendor's thread refused, with a condition. A row joins a collection through `in-collection`, whose target types must have the `container` role, as a type extending `core.collection` does. The kit writes no `position` on it either, and a collection cannot itself be a member, so collections nest through `parent-of`.
- **Files.** A file attaches to its item through `attached-to`, declared with `cascade_on_delete: "with-hosts"` and both ends narrowed to the connector's types, so trashing the item puts its files in the bin and restoring it brings them back. The kit never registers it, and the key holds `--edge-permission attached-to=write`.
- **`retired`** on the connector lists `{ type, connection }` pairs for a connection a row of that type once wrote and no longer does. Keep the connection among `connections` and name it with an empty list on each entry of the type. The kit then removes only the edges it had agreed with that row, in every mode including read only, so a link a person drew is never removed, and never mirrors or puts back a change to it. Without it, a connection an entry stops naming stays on rows written before, because a write replaces only the edge types it names. The key keeps write on the retired edge type.

#### A series and its exceptions

Marfa itself uses `parent-of` to join a changed occurrence of a recurring event to its series, from the series to the exception.

- Declare it among `connections` with both ends the connector's own types, in the direction the vendor names it. A vendor whose exception names its series declares the reverse name `child-of`, read from the exception's side as every declaration is: `many-to-one`, `cascade_on_delete: "cascade"`, the exception's types as `from_type_constraints` and the series' as `to_type_constraints`. The exception's entry names the series in `connections: { "child-of": [{ type, id }] }`. A vendor whose series names its exceptions declares `parent-of` (`one-to-many`, also cascading), and the series' entry names them.
- Declare only one of the two, since they are one edge type. The key holds `--edge-permission parent-of=write` for either.
- The kit writes `parent-of` from the series to the exception in both cases, after checking that the declaration matches the instance's own, which it never registers or changes. For `child-of` the check turns the instance's cardinality about, since it is read from the other end.
- An exception has one series, so naming another moves it, the old connection removed first. A series that has not arrived yet is connected when it does.
- No type among `child-of`'s ends may have a `policy`, since the instance can condition an edge's write only on the version of its source, which is the series.
- A lookup carries only the edges that start at a row, so the kit reads a series from the other end. For eight rows or more of the `child-of` source types, it lists the instance's `parent-of` edges, 500 to a page, and keeps those that point at the rows it is reading, so the cost is one request for every 500 `parent-of` edges in the instance and not one for each row. The pages count every `parent-of` edge, including those of other connectors and of a person's own hierarchy that the key may not read. The kit gives the listing up for one request for each row when the listing would take more pages than there are rows, so a small run in an instance with many `parent-of` edges costs at most twice its rows.
- A rate limit or other failure of these reads fails the run, and the next run reads again.
- Trashing a series in Marfa is carried once, as the trash of the series. The exceptions it took into the bin are not carried separately, and restoring the series brings them back. The connection itself stays while the series is in the bin.

A row a person made by hand with a link value of their own is among them, so asking the vendor about it finds it has no such item. Use it for a vendor whose listing leaves out what it deleted, such as one that lists only open items after it lost its place. It reads every row of the type, 500 to a request, so ask once per type in a run. `{ state: "any" }` adds archived and trashed rows and same-source rows without a link. `includeUnlinked` also returns visible rows from other sources without a link or natural key, to check explicit local requests before importing. `edges: true` gives each row `edges`, its outbound connections as `Item.edges` has them (the first page of each connection type), read in the same pages, so what the rows are connected to is known without a request for each. |
| `inspect(type, { links } or { source_ids })`     | Fresh identity evidence without an agreement requirement: `items` in every state and purge `tombstones`. `source_ids` use the connector's item source. A failed read throws and never proves absence.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `written(type)`                                  | The fields of the type the kit writes now: the `fields` the connector declares, less any the installed type lacks. Where the owner's mapping moves the type's fields, it also holds a mark of that mapping, so a changed template or status override reads in full too. A connector that reads by delta, such as with a sync token, brings a field onto a row it already holds only when the vendor changes the row, so it should include these fields in whatever marker makes it read in full.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

### Tables

A type's `tables` hold many small records that belong to one item and are read with it, such as the checks on a pull request, where a separate item for each would be noise. `tables.put`, `patch`, `remove`, `replace` and `read` take the type, the item's link (or its `source_id` where the type names none), the table and the rows.

- A row is `{ key, values }`. Its ID in Marfa is made from the key, the item and the table (`rowId`), so a run sent again writes the same rows and never a second.
- `put` creates or replaces rows, `patch` sets the columns named (`null` clears one; a row the table does not hold is refused), `remove` deletes rows by key, and `replace` makes the table hold exactly the rows given, writing only those that differ and deleting the rest. `read` returns the rows, or `undefined` where no item holds the key, it is in the bin, or the installed type lacks the table.
- A table on a connector's type belongs to the connector: `replace` deletes every row the vendor did not list, including one a person added in Marfa.
- The plugin installs a type's tables, and the kit registers and replaces none. A stored type that lacks a table, an optional column or a first `order` is written around, with no rows written to that table, and the run names `marfa plugins install <name>`. Any other table change stops the start and names the differences. A changed `label` or `description` on a table or column is no difference.
- Upsert the item first: a call writes nothing for an item Marfa does not hold, or one in the bin, and says so in its report's `skipped`.
- Pages stay within the server's limits (500 operations and 512 KiB). Each call makes one random value, and a page's idempotency key comes from that value, the item, the table and the page's operations. A retry within the call reuses the key, and a later call or run gets a new one, so a value that returns to an earlier state is written again, never replayed from the server's 30-day memory of a key.
- The server writes a page whole or not at all, so a row it refuses, such as a value over a column's `max_length`, is left out and named in the report's `refused` and in a `table-rows:<type>:<table>` condition, and the rest of the page is written. Any other failure throws.

### State

`state.get` and `state.set` keep a small value between runs, such as a sync token. It is kept on the instance, under the key's own source, and only when every write in the run landed, so a connector needs no disk of its own and can start anywhere, empty.

The private state envelope and the explicit problem snapshot must each fit 512 KiB, independently, and each required agreement must fit 16 KiB. A save the server refuses, such as one past its 512 KiB cap, fails the run, so a run never reports success while its progress stands still.

### Scopes and checkpoints

- **`forScope(name)`** binds row calls to one read scope without adding stored scope fields. Await each scoped operation serially. Two unfinished scopes touching the same item cannot checkpoint, so finish one before the other changes that item. Root calls may run concurrently and their shared operations are queued. Mixing root calls with an active scoped operation is refused. An operation or checkpoint left in flight when `run` returns fails the run.
- **`forScope(name).state.get(key)`** is a detached value from the last acknowledged vendor state, including checkpoints completed earlier this run. It does not read the mutable root draft.
- **`forScope(name).state.checkpoint(key, value)`**: await a JSON-compatible candidate after completing that scope's read. The kit clones it, drains that scope's connections, acknowledges its prerequisite agreements, then replaces the existing full state envelope through the same fenced door used at the end of a run. Applicable edges must land first, and absent targets must be durably named in the existing pending connection agreement. A completed checkpoint survives a later failed scope or process restart.
  - The call replaces the explicit JSON value and does not merge vendor fields. When scopes share a map key, build each candidate from that scope's latest acknowledged `get(key)` plus only its completed entry. Reusing a run-wide speculative map could wrongly save an earlier blocked scope's validator.
  - It keeps the last acknowledged log cursor and standing conditions. It neither clears conditions nor rotates a report mid-run.
  - Ordinary row and edge writes are not a transaction and may already have landed when a checkpoint fails, so replay remains necessary.
  - Checkpoints require a successfully loaded state and an active full vendor read. A hinted read cannot advance whole-source progress.
- **The result** is `{ committed: true }` or `{ committed: false, reason }`. The blocking reasons are `row-refused`, `agreement-skipped`, `agreement-oversized`, `connection-unresolved`, `scope-overlap` and `state-oversized`.
  - A nonterminal row refusal blocks even if its usual final-only handling counts no held row.
  - Skipped agreements block conservatively without querying whether the item was hidden or purged. Oversized agreement intentions remain pending rather than being cleared.
  - An unrelated scope can still checkpoint. No refusal journal or automatic cursor is created.
  - Non-JSON input, transport failures, malformed acknowledgments, lost holds and concurrent scoped use throw.
- **A lost acknowledgment.** A clear acknowledgment counts agreements actually deleted, so an accepted clear of a readable item without an agreement correctly returns zero. If either member of a state acknowledgment is lost, different or ambiguous, every later mutation and final save stops, because the server may have committed it and sending an older envelope would roll progress back. The next process reloads authoritative state. The root `state.get/set` API still saves its draft only when the whole run's writes land; a later failure falls back to the latest acknowledged checkpoint.

### Inbound retry journal

A scope may opt into bounded retries of upserts the instance refused: `forScope(name, { retry: { mode: "refetch" | "replay", context } })`, where `context` is a full SHA-256 of the caller's relevant nonsecret retry configuration. `scope.refusals.pending()` returns detached, acknowledged records with a derived `due` flag. The kit does not fetch or replay for the caller.

- **Modes.** `refetch` requires the caller to retrieve each saved exact identity and reconstruct its complete current upsert. `replay` stores a lossless JSON upsert intent, and the caller dispatches due saved operations through ordinary scoped `upsert`. Prefer current complete input over an older replay for the same identity. Missing input, a conditional response or inaccessible input preserves the record.
- **What qualifies.** Only complete `invalid_properties` upserts and singleton `request_too_large` refusals after batch splitting. Refetch stores the complete exact identity, fingerprint, context, refusal and due record; replay must also store the complete round-trip payload. A complete large singleton size refusal may qualify through a genuine point-refetch route even when its replay payload would not fit. File loaders and streams cannot be replayed.
- **What blocks progress.** Unknown refusals, races, incomplete input, skipped bulk results, and undeclared or missing identities block scoped progress. Callers without the capability, and existing unscoped callers, gain no automatic advancement. A refusal the journal takes does not count toward the systemic-refusal check, even when every row in its batch is refused, so a scope whose new rows the instance refuses for their own content still checkpoints. After excluding those refusals, a batch with at least two remaining attempts fails if every attempt is refused with the same code.
- **Timing.** A qualifying refusal and the position commit together in the existing state envelope. Records retain exact identity, intent fingerprint, effective context and due time. Changed intent or context retries immediately; unchanged intent waits 24 hours after an acknowledged actual attempt. A retry refused again is journaled again. Authority, transport and journal-capacity failures still block progress.
- **Clearing.** A successful upsert clears a record only after its row, connections, agreement and state acknowledgment. If the vendor explicitly reports deletion, call `scope.archive(type, keys)` in the same opted-in scope and retry mode, then checkpoint (for linked types, pass the link value as usual). The retry clears with that checkpoint only after an acknowledged archive, an already archived row, or a fresh empty lookup paired with stored evidence that an individual `invalid_properties` insert resolved no existing item when it was refused. An empty lookup alone cannot distinguish absence from a row moved to a type the connector cannot read, so rejected updates, size refusals and records without this evidence remain pending. Failed or uncertain operations, omitted or unhinted identities, and skipped trashed or manually restored rows retain the retry. An absent Marfa row does not establish vendor deletion; that decision belongs to the connector.
- **Limits.** 128 records and 64 KiB of serialized UTF-8 JSON across all scopes, independently of the 512 KiB state envelope. Capacity blocks without eviction or identity truncation: the checkpoint returns `state-oversized`, and the run raises the condition `retry-journal-full:<scope>`. The condition stands until that scope commits a checkpoint, which proves the journal had room, so a run that skips the scope or commits only other scopes does not clear it. Durable refusals remain visible in the complete run log beyond the generic condition-storage cap.
- **Unresolved records.** An unresolved record prevents switching its scope to a different retry mode or removing its capability. Root state setters remain conservative while a journal is unresolved, and independent explicitly capable scopes can still checkpoint from the latest acknowledged map.

### Conditions

- **`log.condition(key, message)`** records something that lasts across runs but lets the run go on, such as a feed that stopped answering among several. Raise it on every run it holds. The kit warns it in the log and carries it in each run's report while it stands, and logs it as cleared once a successful scheduled run reaches its check without raising it. A run that failed, or that deliveries started, clears none, and its report carries what stood before beside what it raised.
- **Limits.** A report has room for about two thousand characters. The conditions that do not fit are counted in it, named in the log and carried first in the next report. Standing conditions are saved separately as the source's explicit `problems` snapshot, with at most two hundred entries and each message cut to 500 UTF-16 code units. Checkpoint and final saves commit both snapshots together. Registration and manager reads expose current problems; a heartbeat or successful report leaves them standing.
- **A run in which the connector read nothing,** because every source it reads failed, is thrown as a failure rather than left to succeed with conditions. What stops the run, such as a vendor refusing the token, is thrown instead and fails the run.
- **`log.unreached({ keys?, prefixes?, exceptKeys? })`** marks the exact checks skipped this run, using exact condition keys or literal key prefixes. Existing matching conditions stand through a successful scheduled run, and a reached check that finds the problem gone can clear it on a later run. Calls accumulate for this run alone. `exceptKeys` excludes exact keys from that call's prefix matches, so a connector can preserve a family with unknown identities while naming the checks it actually reached. Exceptions do not cancel exact `keys` or another call's selectors. Keep unknown identities conservatively when saved progress cannot enumerate every standing condition. Selectors do not raise a condition, create stored state or override a newly raised message. For example, skipping a feed's access check calls `log.unreached({ keys: ["feed-gone:" + feedId] })`; still raise lasting problems with `log.condition` whenever their checks find them.

### Calls to the vendor

- **`signal`** aborts when the process is told to stop or the run's hold can no longer be trusted ([Hold](#hold)). Hand it to every call to the vendor, so a stop is prompt. The kit puts no limit on a run, so combine it with a time limit of the vendor's own, `AbortSignal.any([signal, AbortSignal.timeout(ms)])`, since a call that never ends stalls the run. A call that ran out of time is a failure to answer.
- **A retry deadline.** When a vendor returns one, throw `new Unreachable(message, { retryAt: deadline })` with an ISO timestamp. The kit persists the deadline before continuing and pauses all vendor callbacks, including `preflight` and the reader, until it expires. The deadline also works when a baseline read is throttled before an outbound intent exists. To resume the same callback with its in-memory page cache, await `context.waitUntil(deadline)` instead. The reader, its scoped contexts and the watch callbacks share this durable wait. It saves only acknowledged state, keeps draft state in memory, and resumes only after the deadline has passed and clearing it has been acknowledged. Cancellation or a lost state acknowledgment ends the callback without resuming vendor requests.

## Carrying changes back

A two-way connector declares `link_field` and `onChange`, and the kit's watch phase does the rest. A connector without `onChange` reads the log too: a change made in Marfa to a field it mirrors is put back from what it last wrote, on the next run, and the run names the field.

### How a run goes

1. Before the vendor read, the kit acknowledges pending agreements from its watch observations and completed early carries. An acknowledgment removes ownership only for the exact intent the server accepted. Durable waiting and refusal intent remains in the agreement; acknowledging it does not mean the vendor accepted the change. An unusable prerequisite acknowledgment, including a skipped or oversized intent, a malformed answer, a refusal or a lost response, stops the reader and prevents later agreement retries or state and cursor saves in that process. A new process reloads what the server actually kept.
2. The kit reads the log and compares each row it names with what the two sides last agreed on. What differs is recorded as waiting, from when it was first seen, before the log's cursor moves past it, so a run that fails, or a process that stops, loses nothing still to carry.
3. Creates are carried, and restored rows offered to `remake`. A create goes before the vendor is read, because a run that failed between the vendor's answer and the link would otherwise read the vendor's copy first and create the row's twin.
4. `run` pulls and writes what the vendor had.
5. The rest of what waits is carried. Ordinary outbound field edits run after the vendor read so they can reconcile with its values.
6. The state is kept, and then the run is reported.

The report's `pushed` counts every change carried, landed or abandoned. `own` counts the log's frames showing a row as the connector last left it, which are its own writes. `conflicts` counts each row where a field was decided by the later change.

### The link

`link_field`, in each type's definition, is the property that holds the vendor's own ID for a row.

- The instance keeps it unique within the type, in every state, and refuses a second row holding the same value with `link_taken`.
- With a link, every row of the type is the connector's to read and write, whoever created it and under whatever source. An entry finds its row by the link first and by its natural key second, `archive` takes the vendor's IDs, and a row carrying no value is one the vendor has not been told about. A row counts as told only once the connector and the vendor agreed on it under the value it carries, so a row made by hand with a value of its own is never taken for one the vendor has: a connection to it waits, and `linked` leaves it out.
- Every entry `run` hands over carries the link. One without it is refused with a condition. A type registered before it named its link fails the start until it is replaced with one that does.
- The link is the connector's: a person's change to it is put back, with a condition, before anything is carried by it. A row in the bin cannot have it put back, so its change is carried by the link agreed with the vendor.
- A purge drops what was agreed, so the kit carries one only by a link it can vouch for. That is the agreed link, which it keeps from the moment a run reads a link other than it until the agreed one is written back, for up to a thousand rows. Or it is the row's own link, where every change the run read for the row since then moved it between states, or was the connector's own create, and showed the same link. Any other purge is not carried, and the run names the row. Past the thousand, no purge goes by the row's own link until a whole read of the log keeps every such link again.
- A row whose create was sent and got no link back has no agreed link, so a link it holds since may be a person's. A trash of the row before any later change of it is carried goes with `change.attempted` and no link. The kit keeps, among those thousand, that no link was agreed, so its purge is not carried by that link either.
- A change carried while the row is active goes by the link it holds, and so do its trash and purge after that.
- A connector's own README should say that a row of the type made by hand is carried to the vendor, and that something meant to stay in Marfa is a row of the core type instead.

### `onChange`

`onChange(change, context)` is called once per row with something in Marfa the vendor has not had.

- **`change.kind`** is `created`, `updated`, `restored`, `archived`, `trashed` or `purged`. For a restore, `change.was` says whether from the bin or from archive.
- **`change.item`** is the row as it stands. **`change.changed`** is the fields changed in Marfa and not yet carried, the read-only ones and the link left out. A transition carries the fields changed beside it. A trash and a purge carry none. What of a row travels is the connector's choice.
- **Other fields of a change:** `attempted`, `made`, `refused`, `unagreed`, `placement` and `connections`, described below.
- **The answer.** `onChange` may answer the vendor's entry as its write left it, which the kit takes as what the vendor now holds. A value the vendor normalizes, or its own close echoed back, is then no change. Without an answer the carried values are taken as the vendor's.
  - An answer is written onto the row for each field it states, a `null` as a clear, that the change did not carry and Marfa has not changed since, or that is read-only, such as the number a vendor gave a row it just made, or its reopening on a restore. A field the change carried keeps the person's value.
  - An answer's `connections` are what the vendor holds for each type it names, so a connection the vendor would not take, such as one past its limit, is taken back in Marfa once the run's carries are done. The connector says why with a condition.
  - For a purge, the answer's `changed_at` keeps the purge remembered past the vendor's change carrying it made, such as a close where the vendor cannot delete.
- **Resolving** means the vendor took the change, or there was nothing to send: the kit then takes the carried values as the vendor's. So a handler never resolves after a write the vendor did not take, and never answers one with only a condition.
- **What stops every change,** such as a vendor refusing the token, is thrown as any other error and fails the run. The change waits for the next.
- **`context.setLink(item, id)`** writes the vendor's ID onto a row the vendor just made, retrying once if the row moved since. It keeps the ID with the row's agreement before it writes, so after a create that got no answer the kit can tell that ID from another link the row holds. It throws `LinkTaken` for a value another row carries, and never overwrites a link a row holds, whichever way the write arrives, unless the row's agreement already names that link as the connector's. The kit carries nothing by a link whose agreement does not name it, and raises a condition that says so. Where the agreement kept no ID to be written, the condition says its provenance is unknown and that the connector leaves it alone.

#### When the vendor does not take a change

Throw one of three errors, so that nothing is agreed, the row keeps the person's values over the vendor's next read, the run goes on, and a condition says why until the change lands.

| Error         | For                                                                                                                                                                                       | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Unreachable` | An answer that can pass by itself: a rate limit, a server error, a timeout or no answer.                                                                                                  | The change is sent again next run. Give it a message naming the row. Where many rows can wait on one part of the vendor, such as one account, pass that part as `scope` and a message naming it instead, and the changes waiting on one scope raise one condition between them, saying how many wait.                                                                                                                                                                                        |
| `Refused`     | An answer that will not change by sending again: a value the vendor rejects or a row the account may not change. The message is the vendor's reason, and the kit names the row beside it. | The same change is not sent again. Once the row changes in Marfa, by a person or by the vendor's own read, what differs is sent. A refused edit is sent again once a carried field changes, a cleared one included. A refused trash, which carries no field, is sent again only once the row is restored. A purge is asked again a day after its refusal and its condition stands meanwhile. One refused seven times is given up, with a condition saying the vendor may still hold the row. |
| `Declined`    | A change the vendor is not to be asked about at all, such as an edit to something another person wrote there. The message names the row.                                                  | The fields the change carried are put back to what was agreed, the row's state stays as Marfa has it, the message is raised as a condition, and nothing is tried again until the row changes again.                                                                                                                                                                                                                                                                                          |

- A purge waiting to be carried is kept as the row's own fields and its link, and the kit keeps at most 128 KiB of them, giving up the ones refused most first with a condition, so they cannot crowd out the rest of the connector's state.
- While a refusal stands, `change.refused` marks it. A refused write made nothing, so a create sent after one takes an idempotency key of its own from it, where a key kept across a lost answer would have the vendor answer the refusal again.
- The reason kept with the row is cut to 200 bytes, and dropped where the row's agreement has no room for it beside the refusal. Where it has no room even for the refusal's mark, which the instance's cap on one agreement decides, nothing is remembered and the change is sent again each run, as its condition says.
- Where a create is sent again after a try whose answer was lost, the vendor answers with what that try made, from the values the row held then. Link the row to that item first, then send what the row holds now over it, so a refused update leaves a linked row and the next change goes out as an edit.

#### Other fields of a change

- **`change.unagreed`**: the read-only fields the row holds otherwise than was agreed with the vendor, where putting them back failed. None of them is the vendor's, so a decision taken on one waits.
- **`change.placement`**: for each connection type the vendor holds read only, such as the repository an issue sits in, the rows the agreed connections name, as the vendor was told of them. It says where the row sits as agreed with the vendor, never what a person drew since, so take a decision about where to write or whether to wait on it rather than on the row's own text.
- **`change.attempted`**: when a create, remake, or a trash or purge that overtakes one whose answer was lost, was first sent. The kit records a create before sending it, so a connector whose vendor takes no idempotency key can look for what it made before making another.
- **`change.made`**: where a create made the vendor's object and linked the row but the run then failed, when that create was first sent. Nothing was agreed for the row's fields, so the next change is an update with every field the vendor has not since sent back in `changed`. A connector whose create took fields sends one of them only if it differs from the vendor's object.

### Type options

- **`readOnly`**: fields the vendor holds that are never carried back. Marfa mirrors them: a change made to one in Marfa is put back on the next run, from what the connector last wrote, and the run names the field. Every field is read-only for a connector without `onChange`, or for a type its `carries(env)` leaves out, so any kind can run read only. The link is read-only for every type. It may also name connection types from the type's rows that the vendor cannot change that way, such as the repository an issue sits in. Marfa mirrors them as it does a read-only kind's, putting back a change and naming it, but a create, and `remake`, are handed them in `change.connections`, since they say where the row goes. A create waits until the vendor has been told about each row they name, within the same run where that row is made in it, and the run names a create still waiting.
- **`revive`**: a row in the bin comes back when the vendor changes it, once its trash has reached the vendor, and the run names it. A change only in a `derived` field is not such a change. It comes back as the vendor has it, its close among the fields, where Marfa had not changed them. A trash still waiting to be carried is never undone this way. Carrying the trash must answer the vendor's entry, or the vendor's own close reads as a change and brings the row straight back.
- **`derived`**: read-only fields that say where a row sits, not what happened to it, such as its container's visibility. A change in one is never the vendor's activity: it brings no trashed row back, and a field an agreement never held is no change. A row in the bin is left alone, so it takes the value when it comes back.
- **`carries(env)`** returns the types whose changes go back to the vendor, from the settings. Without it, every type is carried where the connector has `onChange`.

### `remake`

`remake(change, context)` makes a restored row again at a vendor that no longer has it, links the row to what it made, and answers whether it did. It is asked for every `restored` change before the vendor is read. A row the vendor still has answers `false` and is carried by `onChange` after the read. It answers `true` only once the vendor has made the row and it is linked. A remake the vendor did not take throws `Unreachable`, `Refused` or `Declined` as `onChange` does, and is asked again by the same rule. Where a remake failed before, `change.attempted` says when it was first asked, so what it made then can be found.

### States and conflicts

- **A trash in Marfa wins over the vendor:** a trashed row is never written, unless its type revives, and the trash is carried.
- **An archive in Marfa** touches no field and travels beside whatever the vendor sends.
- **A restore** is carried as a restore, made again at a vendor that no longer has the row. Where a trash deletes at the vendor, a change there after the restore means the vendor has the row again. Where it only closes, as for a type that revives, the restore still reopens it.
- **A row the vendor deleted** is archived, and a person's restore of it since is not undone by the vendor's next word.
- **A purge** is carried once, kept on the instance until it lands, so a run that fails first loses none. One the log no longer holds, as after a long time offline, is remembered but not carried. A trash and a purge made between two runs reach the connector as the purge alone, so send the trash's delete again where a vendor that took it answers as already done, and still delete where it did not.
- **A cascade.** A row another row's trash took into the bin, through a connection that cascades, is not the person's trash of it: its trash, its restore and its purge are not carried, and a field changed before it waits for the restore.
- **A conflicted copy is never a create.** When another writer's stale `PATCH` with `conflict=auto` collides with an edit on a `keep_both_copies` property, such as the `body` of a `core.task`, Marfa keeps the losing value in a new row of the same type, under the original's source, without its link, tagged `conflicted-copy` and joined to the original by a `derived-from` edge. The row holds a conflict for a person to resolve, so the kit does not offer it to `onChange` and nothing reaches the vendor. The kit leaves the copy in Marfa, unchanged, and raises one condition per copy, `conflicted-copy:<id>`, that names it. The condition stands, and the kit looks again each run, until the person puts the copy in the bin or removes its `conflicted-copy` tag, after which a copy still in Marfa is carried as a create like any other row. The kit asks Marfa for the tags of a row only when it would otherwise send a create it has not sent before.

### Outbound journal

For an operation whose exact request must survive a restart, use `context.outbound` inside `onChange` or `remake`.

1. Read `outbound.get(change.item.id)` first. If none is pending, await `outbound.save(change, { request, baseline })` before sending HTTP. Both values must be lossless JSON; keep credentials in settings marked `secret`. The returned intent holds a token and detached copies of the captured change, request and baseline. A pending request cannot be replaced, and exceeding the state limit refuses the save before HTTP.
2. Validate a saved request before using it and recover uncertain vendor outcomes using that exact request.
3. Await `outbound.acknowledge(change.item.id, intent.token, answer)` before returning. Omit `answer` to settle the captured values; otherwise supply the vendor's entry as confirmed. Once acknowledged, the kit settles the captured change without calling the vendor again, and deletes the intent only after Marfa acknowledges the agreement. Newer local edits remain pending.

- **Separate from agreements.** The journal is separate from item agreements, so purging a row cannot erase its pending request.
- **Kept on refusal.** A pending intent is retained on any refusal until it is resolved and acknowledged. Replay checks the current kind and row write authority. A read-only kind, lost ownership, missing row or missing handler leaves the intent intact and reports why it waits, while other kinds continue. The affected row is withheld from inbound writes and mirror restoration until recovery is authorized again, so newer local values survive. An uncertain create without a known vendor identity withholds inbound entries for its kind. A queued purge also waits while its kind is read only or no longer declared. Restoring write authority resumes the original request; a missing row never establishes authority.
- **`outbound.advance(itemId, token, { request, baseline })`** is for a multi-step operation. Prove the current step completed, then await it before sending the next request. It returns a new token and preserves the original captured change. A lost replacement acknowledgment blocks sending until recovery reads the durable phase.
- **`outbound.prepareRetry(itemId, token)`.** Only when the vendor response proves the request did not apply, such as a documented HTTP 429 rejection, add `requestNotApplied: true` to the `Unreachable` error. Recovery exposes this evidence on the saved intent. Before retrying the exact request, await `prepareRetry` to consume the evidence durably. A crash or lost acknowledgment after this reset leaves the request uncertain again. A timeout or a throttled readback provides no such evidence.
- **`context.pendingOutbound()`**, in the reader, returns detached snapshots, so inbound admission can withhold identities still being created.

#### A create or remake that a trash or purge overtakes

A create or remake whose answer was lost ends by linking its row, so the person's trash or purge of that row before the next run overtakes it.

- The kit never sends the create again for a row in the bin or gone. Instead the replay calls `onChange` with the person's change: a `trashed` change with the row as it stands, or a `purged` change once the log has shown the purge, which the kit then remembers until it is settled. Either carries `change.attempted`, and `outbound.get(change.item.id)` returns the pending create or remake.
- Ask the vendor with the saved request whether that write made anything, delete what it made, and then await `outbound.acknowledge` with the pending intent's token before returning. A create that never reached the vendor needs only the acknowledgment. Use `outbound.advance` to journal the delete; `outbound.save` refuses, since the intent is pending.
- While the row stays in the bin or gone, later runs hand the trash or purge that delete request. The kit then settles the trash or the purge, not the create, and deletes the intent. A lost acknowledgment is settled the same way on the next run without calling the vendor.
- A refused, unreachable or declined answer leaves the intent pending, as for any other replay. So does a handler that returns without acknowledging it: the run names it in a condition rather than failing, and withholds the row from inbound writes until the intent is settled.
- A row restored before the next run gets the original create or remake replayed, with that write's own request and token from `outbound.get`, even where the trash had advanced the intent to a delete. The delete may or may not have landed, so ask the vendor with the create's request whether its object still exists before linking it or making it again. A row restored after its trash settled is a create again, with `change.attempted`, so the vendor's earlier copy can be found.
- Neither the trash nor the purge carries a link the row holds since the create was sent, which a person may have typed. Each carries only the link the pending write's own agreement held, and a create has none.
- A row another row's trash took into the bin keeps its create waiting, with a condition, until it is restored or purged. A purge the log no longer holds is not seen, so its create keeps waiting too.

### `preflight`

`preflight({ purges, trashes }, context)` guards a whole batch. It runs once before any outbound callback. Do not mutate the vendor in this hook.

- **`purges`** holds every observed purge, including cascade observations, queued retries that are not due, journaled purge operations, and each purge that overtakes a pending create or remake, with its `change.attempted`. It holds every journaled purge, including one the vendor already answered or whose replay waits. The purge snapshots retain properties needed to judge ownership and are not dropped to fit the state limit.
- **`trashes`** holds every trash the run would send, whether carried, replayed from the journal, or sent in place of a pending create or remake it overtakes, each with the row as `onChange` would see it, `change.placement` included. A trash another row's cascade made is not among them, since it is never carried. Neither is a trash the vendor refused that still stands, a journaled trash the vendor already answered, or a journaled trash whose replay waits.
- A row trashed and then purged is among the purges alone, and a row restored before its trash was carried is in neither.
- Count what you need, such as the trashes in each container, read a complete vendor inventory if needed, count any vendor-side cascades, and throw to hold the batch. Marfa's own folders hold a removal only when it exceeds both a number of files and a fraction of the folder, which suits a connector too, so that a small container can still be emptied.
- **A held batch** fails the run before the vendor is read. Nothing is carried, not even the changes the hold does not concern, and the vendor's own changes wait too, because creates and remakes go before the vendor read so that a run never reads a twin of a row it is still making. Everything waiting is offered to `preflight` again on the next run, so the hold stands until the person restores the trashed rows in Marfa or the connector's rule lets the batch through.
- **A trash `preflight` did not see** is sent only after a later run's `preflight` sees it. This covers a row trashed after the run read it, and a journaled trash whose replay could resume only after the hook ran.
- The kit refuses outbound work on an incomplete watch. A connector with this hook also refuses when an expired cursor prevents it from proving the complete purge inventory.

## Receiving webhooks

A vendor that posts webhooks can tell the connector what changed rather than wait for its schedule. The instance stores each delivery as it arrived and never reads it. The connector declares how to read one:

```ts
inbound: {
  // The vendor's signature over the body exactly as it arrived.
  verify: (delivery, env) =>
    verifyHmac({
      secret: env.example_webhook_secret,
      body: delivery.body,
      signature: delivery.header("X-Signature"),
    }),
  // What the delivery says changed, as ids `run` can fetch.
  hints: (delivery) => [
    {
      type: "example.item",
      id: String(JSON.parse(new TextDecoder().decode(delivery.body)).id),
    },
  ],
},
```

- **`verify(delivery, env, signal)`** answers whether a delivery came from the vendor. `verifyHmac` compares an HMAC in constant time: `prefix` for a header such as GitHub's `sha256=…`, and `encoding: "base64"` for a vendor that signs in base64. Declare the secret in `settings` with `secret: true`, so it never reaches a log line.
  - A delivery that fails, or whose `verify` throws, is marked rejected for good and changes nothing. The run says how many with a condition, which usually means the secret differs from the one the vendor signs with.
  - Keep `verify` to the delivery and the environment, since a check that reaches the network can fail for a passing reason and reject a genuine delivery. `signal` aborts on a stop or after ten seconds. A check still running then leaves its delivery waiting for a later run, with a condition, and the deliveries behind it are taken.
- **`hints(delivery)`** answers what the delivery says changed, as the type and ID of each thing `run` fetches, or `"everything"`. A `hints` that throws, as the example does on a body that is not JSON, means everything, and the run says how many with a condition. Neither error's text is kept, since it can quote the body. A delivery is a hint, never the vendor's state: the vendor may send them out of order, twice or not at all, so `run` always fetches what the hint names and writes that.
- **`run` reads `context.hints`.** It is `undefined` on a scheduled run, which reads the vendor whole, and on a run whose deliveries asked for everything. Otherwise it is, by type, the IDs the deliveries named, which may be empty. The run fetches only those and leaves any cursor into the vendor, such as a sync token, where it was, since the rest was not read. Both paths write through `upsert` and `archive`, so a delivery and the schedule reach a row the same way.
- **A run the deliveries started** clears no condition, having checked only part, and reports those that stand.
- **A connector with `onChange`** is handed, beside what the deliveries named, the links of rows with a change in Marfa still to carry, so the run reads what it will write over. A field changed in Marfa is carried only over a row whose entry the run read; the rest wait for the next run that reads them, and the scheduled run reads the vendor whole. A run for deliveries archives only what it was handed, since the rest of the vendor was not read, and with more than two hundred rows waiting it reads the vendor whole.

### How deliveries are taken

- Every run first collects what waits at the connector's inbound endpoints, up to 500, fetching each body to verify it. A body that cannot be fetched leaves its delivery waiting for a later run, with a condition, and the rest are taken.
- A verified delivery that repeats one already processed, or one verified earlier in the same collection, by the header the inbound endpoint names, is marked a duplicate.
- A delivery is marked processed once the run that took it ends without error. A write the run held does not keep it waiting, since the next scheduled run reads the vendor whole and writes it again. A run that fails leaves it waiting for the next.
- A scheduled run that cannot read the deliveries or the inbound endpoints says so with a condition and still reads the vendor whole.
- With `--every`, the kit looks between scheduled runs, every ten seconds or as often as `--look-every` says: for a waiting delivery, for a change in Marfa its vendor has not had (where the connector has `onChange`), and for a change in Marfa to a field it mirrors, which it reads from the log and tells from its own writes. Any of them starts a run for it at once, so a change made in Marfa reaches the vendor, or is put back, within a look rather than at the next schedule. A run that fails, or whose deliveries could not be marked, leaves what waits for the scheduled run rather than trying again at every look. The schedule stays the safety net, since a vendor does not promise to deliver: GitHub does not retry a failed delivery.
- Each run's report counts the deliveries it processed, rejected and marked duplicate.

### The endpoint

The address comes from the instance, never from the kit. With the connector registered, make an inbound endpoint with its own key or a key holding `connectors.manage`:

```bash
marfa connectors endpoints create <connector-id> --label <vendor> --duplicate-header <header>
```

The answer carries the address in full this once, as `path` and as `url` (the address the binary reached joined to it). Later reads show only its last four characters. Give the vendor the instance's public address with that path, and the secret it signs with. `--duplicate-header` names the header a vendor repeats on a redelivery, such as `X-GitHub-Delivery`.

- A scheduled run whose registration holds no live endpoint says how to make one.
- `marfa connectors endpoints retire <connector-id> <endpoint-id>` stops an address answering. A registration holds at most ten live inbound endpoints.
- `marfa connectors deliveries list <connector-id>` shows what waits, with the connector's own key only. A management key is refused, as on every read of the connector's data.

## Running

The environment is `MARFA_API_URL`, `MARFA_API_KEY` and, optionally, the [telemetry](#telemetry) settings. The kit reads nothing else from it. The connector keeps no file: its state is on the instance.

| Flag                      | Runs                                                                                                                                                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--once`                  | One run, then exit.                                                                                                                                                          |
| `--every <interval>`      | A long-lived process. The interval is a whole number with `s`, `m` or `h`, such as `30s`, `15m` or `1h`.                                                                     |
| `--look-every <interval>` | After `--every`: how often the connector looks between runs (ten seconds by default). It is refused for a connector that neither receives webhooks nor carries changes back. |
| `--setup`                 | Setup, once, by hand, for a connector with `setup`.                                                                                                                          |
| `--help`                  | Prints the usage.                                                                                                                                                            |

### `--once`

A run cut short by SIGTERM or SIGINT is not reported, since a run's outcome is only succeeded or failed. The log says it stopped, and what it had already written and agreed is kept, so the next run carries on from it. The connector's state is saved before the run is reported. The private state holds the connector's own values, the log's cursor, and the purges still to carry, each kept until it lands at the vendor. Under `--once` the connector takes the deliveries that wait at its inbound endpoints only when it runs, so a webhook is acted on at the next run.

### `--every`

- **Runs never overlap,** and the heartbeat has its own one-minute timer, apart from the hold's renewals, which are spaced by the instance's window. SIGTERM stops the process cleanly.
- **A failed run** is reported, and the next waits twice as long, doubling up to eight intervals, or as long as a refusal's `Retry-After` names if longer.
- **A run that failed because Marfa did not answer** is asked about instead. The connector checks Marfa every 15 seconds or the interval if shorter, a little spread so connectors do not arrive together, and runs again once it answers. If that run fails for Marfa again too, the backoff applies, until a run succeeds or fails for another cause, which re-arms the quick retry.
- **A key the server refuses,** one narrowed so it no longer writes the connector's types, or one widened past what the kit accepts, which it reads back before each run, stops the process with exit code 3. A setting changed to a value the connector cannot use stops it with exit code 4. Exit code 2 is for an address that cannot be used: a redirect or a malformed URL.
- **A host that is not found,** an untrusted or expired certificate or a refused TLS handshake may mend, as when the connector starts before the network is up. At start it is tried again as a Marfa that does not answer is, and once running it is waited out, each with a warning that names `MARFA_API_URL` and the cause. Under `--once` it exits with code 1.
- **A registration the server no longer holds,** which any door can say (the settings door included, once it has answered for the registration), is made again. So is the check of the connector's types after one of them is deleted from the instance while it runs, which stops the process with exit code 1 naming the type unless the plugin has been installed again. A connector running without fields the installed type lacks checks its types again before each scheduled run, and a second loss within five minutes stops it with exit code 1.
- **A connector that receives webhooks or carries changes back** also looks between runs, every ten seconds unless `--look-every` says otherwise, as in `--every 15m --look-every 30s`.

### Pause, run now and previews

At the start of every run the connector reads what the owner chose for it, once, from `GET /plugins/{name}/connector`. A connector that looks between runs reads it again on each look, to answer previews.

- **Paused:** the host does not start a paused connector. One that is running finishes the run under way: the host wakes it once with `SIGUSR2`, and at the next run start the kit reads the pause, reports nothing as failed, logs one line and exits 0. The host then leaves it stopped until the owner resumes it, and starts it again at its next look. Under `--once` the run is skipped and the process exits 0 saying so.
- **Run now:** the host wakes a sleeping connector with `SIGUSR2`. The run starts at once, as on its schedule, and a signal that arrives during a run makes one more run follow, never two. A run that read a run request reports it as `run_requested_at`, which clears it; a run that read none names none.
- **Previews:** the connector answers each pending mapping preview with the item as the mapping would write it, from the item the preview names or from a recent entry it reads from its vendor, and writes nothing to Marfa or the vendor for it. A connector that looks between runs answers a preview within a look, with no signal; another answers it at its next run. A preview it cannot render, because the item is gone, a template fails, the vendor is down or the result is over 65,536 bytes, is answered with an error. A paused connector answers no preview.
- **A door that does not answer** lets the run go ahead as scheduled, with one warning. A key that is no plugin connector's skips the read.

### Hold

One process runs a connector at a time. Each run is made under a hold on the connector's registration, renewed a third of the instance's window apart, beside the heartbeat, and let go when the process ends.

- **A second process under the same key** waits under `--every`, trying again a second after the hold would lapse, but no sooner than half a minute and no later than its next interval. So a process that took over from one stopped uncleanly runs within minutes, and one standing by beside a live process asks every few minutes. Under `--once` it exits without running. Each says until when it is held.
- **A run whose hold can no longer be trusted,** because another process took it, it lapsed, or five sixths of the window the instance names (`ttl_seconds`) passed since a renewal landed, stops before its next carry and keeps nothing more of what it read. The next run reads it again.
- The instance refuses a write to the connector's state or agreements from any process but the holder.

### `--setup`

Setup registers a connector with its vendor, once, by hand. It is handed:

- **`listen(page)`**, which serves the page at an unguessable local address the log names, for the person to open in a browser, and waits for the vendor's redirect to its `callback`. A page that must name that address, such as a GitHub App manifest's `redirect_url`, is given as a function of it. The browser the vendor sends back is held at the callback, which answers once, until setup ends and it is told whether setup succeeded, or until the listen's `onward(address)`, called once the redirect has arrived, sends it on, such as to the page where the vendor asks for the next step.
- **`endpoint()`**, which makes the connector's own inbound endpoint and answers its address this once.
- **`secret`**.

What setup answers, each by the name of a setting the connector declares, the kit prints on standard output as the commands that set it: `marfa plugins settings <name> --set <setting>=<value>` for a value and `printf '%s' <value> | marfa plugins secret <name> <setting>` for a secret. The owner runs them where `marfa` is signed in as the owner, such as by piping them to `sh`. They hold the secrets in full, so keep them out of a file or a shared terminal.

- Nothing is written to a file. If setup fails, it prints nothing, and every endpoint it made is retired, or named with the command to retire it by hand where the instance would not.
- Each inbound endpoint setup makes is labeled with the connector's label for it and when it was set up, which tells it apart in `marfa connectors endpoints list <connector-id>`, and setup names the ID of each. Once the vendor posts to the new one, retire any it replaces.
- The kit never logs what setup answers, and setup passes anything it logs itself through `secret` first.
- Setup reads the settings set so far from Marfa and needs none of them, but a secret shorter than eight characters stops it with exit code 4, as it stops a run.
- It leaves the registration's read-only types as a connector running beside it set them.

### Exit codes

The process exits with a code that tells its host what to do next (`kit/src/exit.ts`, exported as `exitCode`).

| Code | Cause                                                                                                                                          | What mends it                      |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `0`  | It stopped cleanly, or a `--once` run succeeded.                                                                                               | Nothing.                           |
| `1`  | Any other failure, such as a failed run, a Marfa that did not answer, or a host not found or certificate refused at `MARFA_API_URL`.           | Starting again, after a backoff.   |
| `2`  | The connector's definition or command line is wrong, or `MARFA_API_URL` is malformed or redirected.                                            | A change to the code or the setup. |
| `3`  | Marfa refused the key (`401`, or `403` on the connector's own doors), or the kit refused it.                                                   | A key its host mints again.        |
| `4`  | A required setting is not set, a value is not one the connector can use, or a run threw `SettingsRefused`, as when a vendor ended the sign-in. | The owner changing its settings.   |

### Telemetry

A connector can send its logs and a trace of each run, which carries the error of a failed run, to an OpenTelemetry collector over OTLP/HTTP. Telemetry is off by default: until `OTEL_EXPORTER_OTLP_ENDPOINT` is set, the kit sends nothing of its own, loads no OpenTelemetry code, opens no connection and writes the same log lines. A failed run reaches its owner through Marfa, as a run recorded with its error, which `marfa attention` lists. These are environment variables of the connector's process, apart from Marfa's server, which keeps its telemetry as stored settings with defaults of its own.

| Setting                                                                | Meaning                                                                                                                                | Default                                   |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                                          | The base URL of the collector. Setting it turns telemetry on: traces are posted to `v1/traces` and logs to `v1/logs` under it.         | Unset, so telemetry is off                |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`                                   | The URL traces are posted to, used as written. It needs `OTEL_EXPORTER_OTLP_ENDPOINT` set too.                                         | `v1/traces` under the endpoint            |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`                                     | The URL logs are posted to, used as written. It needs `OTEL_EXPORTER_OTLP_ENDPOINT` set too.                                           | `v1/logs` under the endpoint              |
| `OTEL_EXPORTER_OTLP_HEADERS`                                           | The headers sent with every export, such as the collector's API key, as comma-separated `key=value` pairs with percent-encoded values. | None                                      |
| `OTEL_EXPORTER_OTLP_TRACES_HEADERS`, `OTEL_EXPORTER_OTLP_LOGS_HEADERS` | The headers sent with one signal's exports. They override `OTEL_EXPORTER_OTLP_HEADERS`.                                                | None                                      |
| `OTEL_SERVICE_NAME`                                                    | The `service.name` on everything sent.                                                                                                 | The connector's `name`                    |
| `MARFA_OTEL_SAMPLE_RATIO`                                              | The share of run traces sent, from 0 to 1. A failed run's trace is always sent.                                                        | `1`, where the server's default is `0.05` |

What a connector sends:

- **A trace for each run,** of one span named `connector run`, with the attributes `marfa.connector.trigger` (`schedule` or `look`) and `marfa.connector.outcome` (`succeeded`, `failed` or `stopped`). A failed run's span has an error status and an `exception` event with the error's type, message and stack.
- **A log record for each log line,** with its level as `INFO`, `WARN` or `ERROR`. A line written during a run carries that run's trace and span IDs.
- **The connector's name on everything,** as the resource attributes `service.name` (unless `OTEL_SERVICE_NAME` replaces it) and `marfa.connector.name`, which is always the connector's `name`, beside `deployment.environment`, which is `production`, as the server labels its own.

Everything is redacted as it leaves the process, by the same rule as the log: `MARFA_API_KEY`, each setting `settings` declares as a `secret` or Marfa holds as one, each secret kept with `secret` during a run, and their URL-encoded spellings become `[redacted]`. A header value of eight characters or more is treated as a secret too, so the collector's API key never reaches the log. A connector should not put an item's content in an error, since a message that quotes it as plain prose cannot be told from the error's own words.

Telemetry never fails or holds up a run. An export that takes longer than 1.5 seconds, retries included, is dropped, and the first export that fails is warned of once. When the process ends, including on SIGTERM or SIGINT, it sends what is waiting and gives up after at most 3 seconds. A malformed setting, or a signal's own endpoint without `OTEL_EXPORTER_OTLP_ENDPOINT`, stops the start with exit code 2, naming the setting and never its value, as the server refuses one. Failures found before telemetry starts, including a missing `MARFA_API_URL` or `MARFA_API_KEY`, are logged only.

### The connector host

A connector runs under the connector host. A release of this repository installs that host with one command. [host/README.md](../host/README.md) says how to install it, how it updates and how to turn updates off.

## Converting content

- **`htmlToMarkdown(html)`** from `@withmarfa/connector/markdown` converts the HTML a vendor sends for a `body_field`. Text without HTML passes through unchanged. It throws `NotConvertible` for markup past the kit's limits: 600,000 characters, 25,000 elements and nesting 200 deep. `withinLimits(markup)` from the same module says whether markup is within the first two, for a connector that parses markup with a parser of its own and must not build a tree as large as a vendor can write.
- **`markdownToHtml(markdown)`** converts a body for a vendor that takes HTML. It throws `NotConvertible` for Markdown past 100,000 characters, nested deeper than the converter reads, or costly to convert.
- **`NotConvertible.reason`** is `length`, `elements`, `depth`, `complexity` or `unreadable`. The connector handles it by leaving the field out when reading, and by refusing the write when sending.

## Fetching pictures

`fetchPicture` from `@withmarfa/connector/pictures` fetches a picture a vendor names by a web address. It returns the picture's `bytes` and `mime_type` for a `FileSource` to upload, or `{ ok: false, reason }`. For `bad_status` the result also carries the answer's `status`, so that a 404 can be told from a 429 or a 503.

- It makes one `GET` over `https`, with a fixed `User-Agent` and no credentials, cookies or referrer, and follows at most four redirects.
- It refuses an address that is, or resolves to, this machine or a private network, at the first request and at every redirect, unless the connector passes the host in `privateHosts`. `privateHostSet` from `@withmarfa/connector/network` reads a setting's value into that set.
- It stops at 25 MiB, by the length the server declares and by the bytes it sends, and after 30 seconds.
- It decides the type from the first bytes, never from the server's header: PNG, JPEG, GIF, WebP, AVIF and HEIC are pictures, and SVG never is.
- It reads the size from those bytes, and refuses a picture one pixel wide or high, a picture that claims more than 100 million pixels, and the counting pixels of known trackers.
- The reason is one of `invalid_address`, `not_https`, `private_address`, `tracker`, `too_many_redirects`, `bad_status`, `too_large`, `timed_out`, `fetch_failed`, `not_a_picture`, `svg`, `one_pixel` and `too_large_dimensions`. A connector keeps the code, not the words.
- The function throws only when the `signal` it is given aborts.
