# plugins

WithMarfa's plugins for Marfa. What an owner adds to a Marfa is a plugin: a connector, a family of common types (`common.*`) with guidance on using them, or both. This repository holds the connectors, built from source today, and the kit and template they are built from. It also holds the common type families, each a plugin that a release publishes for `marfa plugins install <name>` to read, starting with Tickets (`types/tickets/`). Never call this a directory, registry or marketplace; Marfa's docs keep their Catalog as the reference of everything a Marfa can hold. The Marfa plugin for Claude Code and Codex is withmarfa/marfa-plugin, a different thing.

For connectors: a small kit makes a connector a page of code, a template to copy, and the connectors themselves, one folder each. A connector is a process with the key its connector host mints: it registers itself with an instance, reads its settings from Marfa at the start of every run, and checks the types and connection types its plugin installed against its build, registering none (installing the plugin registers them, and the key holds no metadata entry; a difference it can write around, an optional field or table the installed type lacks, is one condition naming `marfa plugins install <name>`, and any other stops the start), heartbeats, pulls from its vendor, reads what its vendor posts to its inbound endpoints, writes what it finds as the owner's mapping says (read at the start of every run: each kind on or off, on its own type by default or on the target type the owner chose, and each target field filled from a field of the kind, a fixed value or a MiniJinja template, with status words moved through their group; a fixed or templated field is never carried back), carries changes made in Marfa back to the vendor where its brief says so, and reports each run. It writes to the vendor only through the kit's watch phase. A connector writes the tier the owner's mapping chose, `feed` by default: a create names no tier, and the server gives it the kind's mapped tier. Moving an item between tiers otherwise is a person's or an app's act.

## Layout

- `types/`: the common type families, one folder each, `types/<name>/`, with `types/README.md` saying what a family is. A family is a plugin's source folder: a `plugin.json` (`name`, `title`, `description`, `mark`, `maker` and `marfa`, the oldest Marfa release it supports; never a `version`, which a release stamps from its tag), a `types/` folder of definitions with the guidance for `<id>.json` in `<id>.md` beside it, and optionally `edge-types/`. A folder of `types/` with no `plugin.json` fails the check. The plugin a connector generates will be the same folder at `connectors/<name>/plugin/`. A published family only ever gains fields, status words and types.
- `kit/`: the reusable connector runtime package `@withmarfa/connector`.
- `shared/`: private workspace packages shared by related connectors, today the Google sign-in in `shared/google`.
- `template/`: what a new connector starts from. `template/connector/` is copied to `connectors/<name>/`; beside it are its README, a LaunchAgent and a Dockerfile.
- `connectors/<name>/`: one folder per connector, run and never published.
- `connectors/<name>/plugin/`: the plugin each connector is published as, in the shape `types/<name>/` has (`plugin.json` with a `connector` section, `types/<id>.json` with `<id>.md` beside it, `edge-types/<id>.json`). Everything but the Markdown is generated from the connector's `connector()` in its `src/definition.ts` (`src/main.ts` only starts it): `title`, `mark`, `maker`, `source`, its `settings` (each a `name` in lowercase snake case, a `label`, a `kind` of `text`, `number`, `boolean` or `choice`, `secret` for text only and never with a `default`, `default`, `required` and `choices`) and its `types`, each a kind with a `name` and a `direction`. The connector's `edge_types` are the edge types of its `connections`, its own and Marfa's, so the key a host mints writes exactly those. A host-minted key writes only its kinds' types, so a definition declares every type the connector can ever write in its widest shape; one that changes with a setting takes the settings as `connector(settings)`, `main.ts` hands `connector` itself to `main`, which builds it again from the settings Marfa holds at the start of every run, and the definition exports `widest`, the settings that give it its widest shape, which the generator builds it from. A definition reads no `process.env`. After `pnpm build`, `pnpm connectors:generate` rewrites the JSON and `pnpm connectors:check`, which `Checks` runs, fails when any is out of date, when a type has no guidance or when a guidance file has no type; never edit the JSON by hand. Write each type's guidance, at most 1,000 characters, in `types/<id>.md`.
- `scripts/`: the script that fetches the pinned release's server and `marfa`, `check-plugins.ts` and `release/` (the release build, and what a plugin owes the published versions), the proof harness, which builds a connector of its own on the kit, with the vendor stubs it shares with the connectors' tests, and tests that refuse a version in a manifest or a file holding one, a home directory, machine name or personal address, tracked build output, a package left out of the build, and a workflow job off standard GitHub-hosted runners.

## Commands

Use Node 22.13 or later for pnpm 11; the connector runtime supports Node 22.12 or later. `pnpm install --frozen-lockfile` installs the published client pinned exactly in the kit and scripts manifests. Then run `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` and `pnpm test`. No server checkout is needed for those commands or image builds; `pnpm test` also runs the pinned `marfa`, so run `scripts/monorepo.sh` before it too.

Before `pnpm test` and `pnpm proof`, run `scripts/monorepo.sh`. It downloads `marfa-server` and `marfa` from the withmarfa/marfa release whose tag names `scripts/monorepo.commit`, verifies the archive against the release's checksums and leaves them in `vendor/marfa-server` and `vendor/marfa/marfa`; `MARFA_SERVER_BIN` and `MARFA_BIN` name others. Three proof groups need test hooks, which a release server lacks: two shorten the connector hold, and `google-sign-in` points a connector's sign-in at a stand-in provider with the `sign-in-provider` fault. They boot the server `scripts/monorepo.sh hooks` builds from that commit into `vendor/marfa-server-hooks` (`MARFA_HOOKS_SERVER_BIN` names another). After a connector build, the proof boots the server on a free port, claims the owner through its control socket and uses the installed registry client against it. A proof group that starts a connector first installs its plugin with `marfa plugins install <folder>` (`scripts/proof/install.ts`): the generated `connectors/<name>/plugin/` folder for a connector of the repository, and a folder made the same way from its definition for a connector the proof defines, which exports `connector` and starts only when run as a program. The folder holds the `connector` section for a connector of the repository, and for a connector of the proof's own that declares settings. The proof plays the owner and the host (`scripts/proof/host.ts`): it makes a connector host and redeems its link, assigns each such plugin's connector to it, mints the connector's key through the host's door, and sets the connector's settings through the owner's `PATCH /plugins/{name}/connector/settings` before each run. A connector of the proof's own that declares no settings reads what the proof tells it from the environment and runs on a key the control socket mints.

The pin moves by itself. `.github/workflows/follow-releases.yml` runs from `main` only, daily and by hand, and keeps the connectors on the newest published (not draft, not pre-release) release of withmarfa/marfa. When they are not on it, the release is not behind the pin, `@withmarfa/client` at the release's version is on npm, and no open pull request changes `scripts/monorepo.commit`, it moves `scripts/monorepo.commit` to the commit of the release tag and `@withmarfa/client` to the release's version in the kit and scripts manifests, and regenerates the lockfile. The first job holds no secret and hands the change to a second as a patch; the second refuses a patch that touches anything but those four files, applies it, and opens a pull request as the WithMarfa Bot app on the branch `automation/marfa-release`, titled `chore(marfa): follow marfa release <tag>`, with auto-merge armed (the checks on a pull request that the GitHub token opens wait for someone to approve them, so it uses the app's token, limited to contents and pull requests). The repository's checks, the proof included, decide whether it merges; one that fails stays open and stops the next, and the session that finds it fixes it or closes it. A by-hand run is a dry run unless `dry_run` is turned off (`gh workflow run follow-releases.yml --ref main -f dry_run=false`), and it is safe to start twice, and right after a Marfa release, since a second run finds the pull request open or the connectors already on the release. `scripts/follow-release.sh` holds the decision and the write, and `scripts/test/follow-release.test.ts` pins them. To move the pin by hand, look for an open pull request that changes `scripts/monorepo.commit` first, run `scripts/follow-release.sh apply <commit> <version>`, then `pnpm install --lockfile-only`, `scripts/monorepo.sh` and the proof. Merging the pull request starts no release: a version here is a tag made by the session that finishes a logical set of work (Versions).

`node --experimental-strip-types scripts/check-plugins.ts` runs `marfa plugins check` on every plugin source folder, as installing will judge it, and fails naming each folder that is refused. `node --experimental-strip-types scripts/release/release.ts build --version <version> --out <empty folder>` builds every plugin's bundle at that version, `plugins.json` and `checksums.txt` there; `publish --tag v<version> --dir <folder>` creates the release from them (`--dry-run` creates nothing). `pnpm proof --group plugins` runs the proof's plugin group alone.

## Secrets

A connector's settings and secrets are held in Marfa, set by the owner with `marfa plugins settings <name> --set` and `marfa plugins secret <name>`, and read by the kit at the start of every run through `GET /connectors/{id}/settings`, which opens a secret only to the key its connector host minted. The environment holds only `MARFA_API_URL`, `MARFA_API_KEY` and the telemetry settings. The kit redacts every secret from the log, conditions, run reports, errors and telemetry as soon as it reads it. `--setup` prints the commands that set what it made, and writes no file. Nothing here holds a value.

## Exit codes

A connector's process exits `0` once stopped cleanly, `1` for any other failure, `2` when its definition or command line is wrong or `MARFA_API_URL` is malformed or redirected (a host not found or a certificate refused may mend, so it is `1`, or tried again under `--every`), `3` when Marfa refused its key (`401`, or `403` on the connector's own doors) or the kit refused it, and `4` when a required setting is missing, a value is invalid or a run threw `SettingsRefused`, which a connector does for what only its owner can mend, such as a sign-in its service ended (`kit/src/exit.ts`). The kit's README (`kit/README.md`) says what mends each.

## Versions

- Every version is the previous one plus 0.0.1, whatever the size of the change. Numbering starts from 0: the first version is 0.0.1.
- A version exists only as a git tag. A tag is created when a logical set of merged work is ready, by the session that finishes that set unless its brief says not to, and no one writes a version into a file.
- Pushing the tag `v<version>` runs `.github/workflows/release.yml`. One release runs at a time. It stops when a release for the tag exists, or when the tag is not later than every plugin the latest release lists, and when there is no plugin; it builds every plugin's bundle at that version, runs the proof's `plugins` group, which installs each plugin over the bundle the latest release lists and fails if the server refuses it as narrowing (`plugin_narrows`), then publishes a GitHub Release marked latest, holding the bundles, `plugins.json` and `checksums.txt`, with build provenance attested. A release is never overwritten, and every release holds every plugin at its tag, so a reader can fetch `releases/download/<tag>/plugins.json` for an exact version. A manual run builds all of it and publishes nothing. Connector code bundles and host archives are added in `extraAssets` of `scripts/release/release.ts`.

## Writing

- Public prose (README, docs, issues, pull requests) follows the Google developer documentation style guide, in American English, with docs organized by Diátaxis: tutorials, how-to guides, reference and explanation kept apart.
- A change that a reader of Marfa's docs would notice opens an issue on withmarfa/docs saying what changed, why and for whom; it does not edit the docs.
- Code comments follow the language's own conventions and survive only if they explain a why the code cannot; when in doubt, they go.

## In force

- American English in code, comments and commits. Scoped Conventional Commits (`feat(kit):`, `fix(rss):`).
- Feature branches and pull requests; never push `main`. A session merges its own pull request once the review its risk calls for is done, with that depth stated on the pull request: squash, branch deleted. It waits for every required check, except as the next point allows.
- Getting finished work to `main` comes first. Branches need not be up to date with `main`, so update one only for a conflict or for something on `main` it needs. When `main` is red, fix it first in one small pull request, because a red `main` fails every open pull request's checks. An admin merge (`gh pr merge <number> --squash --admin --delete-branch`) goes ahead without waiting for `Full CI` in five cases, and the pull request says which: jobs the change cannot affect; check bookkeeping on a head that passed its full checks; a fix for a red `main` that changes only tests, once its local quick checks pass; a pull request that failed only because `main` was red, once `main` is fixed, when the only failed jobs are the ones `main` broke and its local quick checks pass, with no rebase and full rerun; and a clean update from `main` of a head that passed `Full CI`, once the run the update starts is cancelled and `git diff origin/main...HEAD` shows the same change as before the update. GitHub merges no draft, so mark one ready and cancel the run that starts first. After an admin merge, watch the merged commit's runs on `main` and fix `main` forward if one fails. A change to data, access, the Marfa pin (`scripts/monorepo.commit`), a migration or a release always waits for `Full CI` to pass.
- Make worktrees in `.claude/worktrees/` (`git worktree add .claude/worktrees/<name> -b <branch> origin/main`). Once the work is merged, remove the worktree and its local branch (`git worktree remove`, then `git branch -D`, because git sees a squash-merged branch as unmerged) and run `git pull --ff-only` on `main`. If git refuses a removal, report it rather than forcing it.
- This repository is public while development continues. Public visibility is not a release milestone.
- Every Actions workflow uses standard GitHub-hosted runners, never personal self-hosted runners or paid third-party runners. Never hold back a push or a check to ration runners; keep stacked changes in order and cancel superseded runs.
- `scripts/ci-changes.ts` decides what a pull request or a push to `main` runs. `Checks` always formats and scans every file, and builds, typechecks and lints for a change to code: it is the quick job. `Tests` runs the unit tests in three shards (Vitest `--shard`), `Proof` runs the proof in three shards, and `Image` builds the template's image for the template and each connector, checks its client version, contract and runtime/type bytes against the frozen registry install and checks the LaunchAgent example, and `Plugins` runs `marfa plugins check` on each plugin's source folder with no dependencies installed, each only for a change that can affect it. A change that touches only `scripts/proof/` runs `Proof` alone, except the files a unit test imports, which also run `Tests`. A change that touches one connector and nothing in `kit/`, `shared/` or the template runs that connector's tests only (`scope`); any doubt runs everything. Anything under `types/<name>/` or `connectors/<name>/plugin/` is that plugin's code, Markdown included, since a type's guidance is Markdown: it runs `Plugins` and `Proof`. Other Markdown, the license and the settings and instructions under `.claude/`, `.agents/`, `.codex/` and `.githooks/` are documentation, and an unnamed path, a fixture, a workflow, an empty or unreadable diff, a schedule and a manual run run everything. A push to `main` is classified the same way, but only when the commit before it has a green `ci.yml` push run, and runs everything otherwise, so a documentation commit never shows green over one that was red or unchecked. A skipped job passes its required check; `scripts/test/ci-changes.test.ts` pins the rules. A draft runs only `Checks` without its tests; marking it ready for review, and every push after, runs everything.
- The proof is a list of groups in `scripts/proof/shards.ts`, each a `prove` function with the statements it makes and the seconds it took. A shard runs the groups that a split by longest time first gives it, the same in every process, and boots its own server, which the shard's groups with `instance: "shared"` use together; a group with `instance: "own"` boots a server of its own, empty, because it installs plugins or holds a source that another group's connector would hold on a shared one. A new group needs its entry there and its runner in `scripts/proof/main.ts`; with no time given it is weighed at a minute. Refresh a group's seconds when its time changes a lot. `pnpm proof --group <name>` runs one group, which is how the release gates itself. The GitHub group is one stateful flow, so it sets the length of the longest shard.
- A test that fails runs once more in CI (`retry` in `vitest.config.ts`), and `scripts/retried-tests.ts` lists each one that then passed in the job summary and as a warning. A test reported more than once gets an issue and a fix. A test never asserts how long something took: it counts the work, or it relies on the test timeout to end a hang.
- On a pull request, a failed `Checks` makes the `stop` job cancel the run, so `Tests`, `Proof` and `Image` stop; it never runs on `main`. The last job, `Full CI`, waits for every other job and fails if any failed or was cancelled, and it still runs after that cancel, so it reports failed and not cancelled. On a draft it is named `Draft CI`, so the required `Full CI` stays expected, and blocks a merge, until the run that marking it ready starts has finished; skipped jobs therefore cannot let a pull request merge in the moment between marking it ready and the first full run. `Full CI` and `Pull request description` are the required checks, since a merge waits only on required checks. Each job's time limit is about twice its usual longest time; keep them that way when a job gets slower or faster.
- A scheduled workflow that fails (`audit.yml`, `follow-releases.yml`) runs its `report-failure` job, which opens one issue titled `Scheduled run failed: <workflow>` and comments on it for each later failure (`scripts/report-scheduled-failure.sh`). The weekly dependency audit is not a required check.
- `.github/workflows/codeql.yml` analyzes a push to `main` and a pull request that is not a draft, and the whole tree once a week, unless a change is only Markdown, the license, `.claude/`, `.agents/`, `.codex/`, `.githooks/` or `.github/ISSUE_TEMPLATE/`. It is not a required check, so a `paths-ignore` filter starts no run at all for documentation; `scripts/test/ci-changes.test.ts` pins it.
- Every action is pinned by commit with its tag in a comment, and the Dockerfile's base image by digest; Dependabot keeps them current and `scripts/test/tree.test.ts` refuses one that is not.
- No personal detail of any machine or person in this repository: no absolute paths, hostnames, account names or credentials. Configuration comes from the environment.
- Removed means gone: no shims, no aliases, no compatibility paths.
- TypeScript, strict, on Node 22 or later. The transport to Marfa is `@withmarfa/client` and nothing else. The kit exports telemetry over OTLP only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and loads that code only then. A failed run reaches the owner as a run recorded in Marfa, with its error, and a start that fails before the connector is registered is logged, and exported over OTLP when that is on. Failures found before telemetry starts, including a missing `MARFA_API_URL` or `MARFA_API_KEY`, are logged only.
- Marfa sends nothing about itself until its owner sets where: no vendor token, name or dependency in this repository's shipped code, and nothing sent by default. The rule is in withmarfa/marfa's `AGENTS.md`; the `names no analytics vendor` test in `scripts/test/tree.test.ts` enforces it here.

## Code Review Rules

Report only a real problem: one that breaks the issue's acceptance criteria, a rule written in this file (quote it) or correctness, and say how it fails: the input, state or step, and what goes wrong. If you cannot say how it fails, it is not a finding. Leave formatting, lint and anything CI catches to CI, and skip any convention that is not written down. Check the whole tree, not only the diff, and name each finding by the check it breaks.

- **Done.** The acceptance criteria are met, the change was run for real in the conditions it will meet and not only compiled, new behavior has a test that was seen failing first, and what the pull request claims is true. A test that asserts absence has a witness: the same path with the condition removed produces the thing.
- **True.** A comment, doc, instruction file or contract statement the change touches or leaves untrue is a finding, fixed in the same change. New prose follows the standard under Writing for its kind. A claim of completeness ("all callers updated") is checked by searching, not accepted.
- **Nothing left behind.** Dead code, shims, old names and references to removed things.
- **Every path.** A permission, check or interpretation of a value holds at every door, including one the change adds, and in every copy of the logic: the server and the working copy, a fallback, a retry. Nothing is exempted by a name or field someone else controls.
- **Check and write are one step.** A decision is made on the state the write commits, with no wait, retry or asynchronous boundary between. Intent kept for a retry is captured, unchangeable, when it is sent, and announcements follow the order the writes were admitted.
- **Report only what is known.** Success, absence, completeness and current authority are claimed only on evidence that proves them: a refusal does not prove a write never committed, an old receipt does not prove present access, a partial snapshot is not a full inventory. A failure is not cleared by an unrelated operation.
- **Keep what people made.** A refused, failed or uncertain write is kept where the person can get it back, never dropped or rolled over newer work. Clean-up acts only on what it proved gone, and an edit keeps every byte it did not mean to change.
- **Real conditions.** Real clocks and dates, number ranges across languages and SQLite, runtime limits, slow or absent peers, untidy input, other platforms and file systems. One bad item, slow peer or hiccup stays contained and never takes down the batch, the folder or the job.
- **Nothing leaves by default.** A change that makes anything leave the owner's machine with no destination set, or that adds a vendor name, token, setting or dependency to shipped code outside the vendor check's allowlist, is a defect.
- **Flaky tests.** An unexplained flaky test is a finding: reproduce it, or say exactly why it cannot recur.

Mark a finding blocking when it changes how Marfa behaves or breaks a criterion or rule, and a quick fix when it is a name, a stale reference or a wrong count. Keep a problem that was there before the change apart from findings against it, and list it only if it is clearly wrong and would keep coming up.
